## 本批记录但不修（D-127）

- **`search_items` 无上限返回**：它返回完整 `ItemSchema`（全部元素 + 标签），事项多了就是无上限的 token 灌入——与 `search_raws` 的「2,000 字预算 + 截断标注」口径不一致。本轮**不修**（用户 2026-10-22：「剩下两个都可以暂时不动」）。修法方向：与 `search_raws` 共用同一套预算/截断机制（摘要级返回 + `truncated`/`more`），而不是给它单独定一个数字。触发条件：事项量上来后 AI 实际出现上下文被撑爆、或 token 账单可见地上涨。
- **跨表按元素反查批次**（AI 想搜「包含某元素的所有批次」）：要跨 `fragments` → `evidence` → `item_versions.snapshot` 三表反查，比 FTS5 复杂得多。本轮**不做**——FTS5 搜内容原文 + `search_items` 搜事项已覆盖主要场景。触发条件：真实使用中出现「按元素找批次」的反复需求。
- **拼音检索**（搜「tushuguan」命中「图书馆」）：jieba 词典不带拼音，需要额外词典 + 转换层。本轮**不做**——中文输入法下用户/模型都直接打汉字。触发条件：出现真实的拼音输入场景。

## 本特性不处理（记录备查，D-127 调研发现）

- **并发批次抢同一段系统提示词缓存前缀**：实测同一次消化里 13 次调用分布在 5 个并行批次上——多个批次同时消化时会共享同一段系统提示词前缀，缓存命中率被彼此稀释（实测 prompt 涨 5,000 token 时命中率 95%→55%）。这与「批内连贯推理链」是两件事，**靠改提示词布局解决不了**（除非串行化消化，那会牺牲吞吐）。本轮记录备查，不处理。
