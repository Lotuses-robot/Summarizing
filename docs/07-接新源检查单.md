# 07 · 信源开发指南（D-88 定稿；样板源 = chat，参照实现 = nc）

> **本文件 = 「接入一个新信源」的唯一说明书**。上游：D-84（信源化源架构）、D-85（存疑库）、D-88（契约重设计八件套）。
> **验收锚点（唯一硬指标）：照本指南能独立写出一个新信源**（04§五：掐表 ≤ 30 分钟为达标）。
> 参照物：样板源 chat（`application/chat.ts` 的 ingest 工具，无适配器）；**唯一完整适配器 = nc**（`apps/server/src/sources/nc/`）。

---

## 一、30 秒总览：信源是什么、不是什么

- **信源 = 源适配器**：一个源一个目录（`apps/server/src/sources/<源名>/`），实现 `SourceAdapter` 接口、注册表（`sources/registry.ts`）加一行。core 不感知你的协议，**core 装配（`makeApp`）甚至不知道有哪些信源**。
- **变数全留给你**：解释协议、打包（要不要合并碎片）、管设置——都是你自己的事；core 只提供「手段」（`SourceContext`）与「场地」（webhook 网关内的命名空间，`WebhookRegistrar`）。
- **「信源」≠「插件」**（D-88 术语定稿）：插件 = 未来更大的扩展体系（信源将是它的子类）。本指南只讲信源。
- **不是**：不做 manifest、不做运行时加载/沙箱、不做依赖编排、不做自动发现（D-88「明确不要」清单）。

### 你的源要不要经 Router？先回答一个问题

**「一个外部入口要服务多个账户吗？」**

| 答案 | 走哪 | 例子 |
|---|---|---|
| **是**（一个回调 URL，多个客户各自归属不同账户） | **Router**（`apps/server/src/router/`）+ 一个只做消化的信源 | 微信客服（D-128/D-130） |
| **否**（地址里已经带着账户令牌，进来就知道归属） | 信源自管 hook，**不经 Router** | nc（`/hook/<令牌>/nc/event`） |

**Router 与信源的分界（D-130 定，越界即返工）**：

| | Router（部署级，一个） | 信源（每账户一个） |
|---|---|---|
| 认识账户 uid | ✅（查绑定） | ❌（**绝不**） |
| 碰账户库 | ❌（**绝不**，只调 `accept`） | ✅（经 `ctx.ingest`） |
| 验签/解密/拉取/游标 | ✅ | ❌ |
| 查绑定 / 发回执 | ✅ | ❌ |
| **协议字段**（分组键、identity、正文） | ❌（只读分流必需的路由字段） | ✅ |
| 缓冲 / 切段 | ❌ | ✅ |

**Router 只交给信源两样东西**：`accept({ raw, receivedAt })`。`raw` 是它**不解释**的原始消息，
`receivedAt` 是它记的到达时刻。分组键与 identity 全由信源自己算——这是「Router 不认识协议」
的结构性保证（想多读一个字段，就得在 Router 里显式加一行，评审看得见）。

**加一个经 Router 的新源的最小成本**：`router/<协议>/ingress.ts` 导出一个对象
（`start?` / `stop?` / `register(app)` / `fetchMedia?`），在 `router/index.ts` 的
`ingresses` 数组里加一行，再在 `sources/registry.ts` 加一个只做消化的信源。`app.ts` 一行不用改
——路由路径由接入自己声明。

## 二、契约：`SourceAdapter` 与八件套（完整签名）

> 单一来源：`apps/server/src/sources/types.ts`（本文照抄，改契约先改那里再改这里）。

```ts
// import type { FastifyRequest, FastifyReply } from "fastify";

/** 信源 webhook 登记口（006 收窄，D-96）：只在本源命名空间内登记 HTTP 入口——
 *  可达地址 = /hook/<账户令牌>/<源名>/<path>；core 网关统一鉴权路由。
 *  路径为**纯字面段**（不支持 :param——需要参数走 query/body）。
 *  信源不能再挂全局路由（多用户下=鉴权旁路）；拉型源（SSE 等）不用它，走 start()。 */
export interface WebhookRegistrar {
  post(path: string, handler: SourceRouteHandler): void;
  get(path: string, handler: SourceRouteHandler): void;
  put(path: string, handler: SourceRouteHandler): void;
  delete(path: string, handler: SourceRouteHandler): void;
}

/** 信源适配器：一个源一个目录，实现本接口、注册表加一个**工厂**（每空间各造一份）。 */
export interface SourceAdapter {
  /** 源的唯一短名——source、信源设置命名空间、from 排障标记共用。 */
  readonly name: string;
  /** 接收一条原始消息（D-130）。**两个调用方**：Router（部署级，一对多接入）／
   *  信源自己的 webhook（nc，地址带账户令牌）。解协议、算分组键、组装 identity 全在这里。
   *  失败**不抛**——返回 `{ok:false, reason}` 让调用方留痕。 */
  accept(input: { raw: unknown; receivedAt: string }): AcceptResult;
  /** 上岗（装配期，同步）：登记 webhook（`registrar`）、起定时器、存引用——不阻塞、不连外部。
   *  ⚠️ 006 起装配按**空间**（每账户）各跑一次——适配器必须用工厂造实例（私有态天然隔离）。 */
  register(ctx: SourceContext, registrar: WebhookRegistrar): void;
  /** 启动（可选）：可异步、可失败。失败只标记本信源 error，不拖垮别的。nc 就不需要写。 */
  start?(): void | Promise<void>;
  /** 停止（可选）：清自己的运行态（如强制封批缓冲）。core 关闭时调用。 */
  stop?(): Promise<void>;
  /** 声明设置项（纯数据）。缺席 = 无设置。core 落库并随 GET /api/sources 吐给前端。 */
  settings?(): SettingField[];
  /** 接入引导（纯数据，可选）：告诉用户怎么在你的系统里把 webhook 指过来。
   *  缺席 = 设置页不显示引导行。文案归你，前端不认识任何源名（D-115）。 */
  guide?(): string;
  /** 声明活动信号（纯数据，可选）：设置页卡头徽标显示哪些指标、各叫什么。
   *  **声明顺序 = 展示顺序**；你在自认为发生活动的时点调 `ctx.markActivity(key)`。
   *  保留键 "ingest" 由 core 在成功落库时自动打点、重启后从库里恢复——不要重复声明它（D-115）。 */
  activity?(): ActivitySignal[];
}

/** 一条活动信号声明；`key` 是你自己起的标识，`label` 是给用户看的短词。 */
export interface ActivitySignal { key: string; label: string; }

/** core 交给信源的手段（八件套）。刻意无 db——信源不摸数据库。 */
export interface SourceContext {
  readonly name: string;                                                    // ② 自我标识
  ingest(batch: SourceBatch): { ok: true; id: string } | { ok: false; reason: string }; // ⑤ 投递口
  getSetting(key: string): unknown;                                         // 设置读写（命名空间隔离）
  setSetting(key: string, value: unknown): void;
  log: { debug(msg: string): void; info(msg: string): void; warn(msg: string): void; error(msg: string): void }; // ① 日志口（core 加前缀）
  onCleanup(fn: () => void | Promise<void>): void;                          // ③ 清理注册表
  setInterval(fn: () => void, ms: number): void;                            // 定时器助手（自动登记；core 关闭时统一撤销）
  reportError(err: unknown, opts?: { fatal?: boolean }): void;              // ⑥ 错误出口
  markActivity(key: string): void;                                          // ⑧ 活动打点（须先在 activity() 声明；未声明 → 忽略并留痕）
}
// SettingField 六型：text / number / boolean / select / record / secret（key/type/label/description?；default? 仅 text/number/boolean/select/secret 有，record 无）
```

**八件套每件的「为什么」**（业界依据：HA / VS Code / Telegraf / Obsidian 横向对比，决策见台账 D-88）：

| # | 手段 | 为什么存在 |
|---|------|-----------|
| ① | `ctx.log` | 你不该自己写 `process.stderr`——core 统一加 `[source:<名>]` 前缀，日志可按源过滤 |
| ② | `ctx.name` | 日志前缀 / 设置命名空间 / 错误归属共用，你不用自己再定义常量 |
| ③ | `ctx.onCleanup` | 一个信源有多个资源（定时器+监听器+socket），core 关闭时按**单源内后注册先撤销**逐项清理；返回单个清理函数容不下 |
| ④ | `settings()` + `ctx.get/setSetting` | 设置项声明成**纯数据**（六型），core 落库 `__schema__`，前端按 schema 渲染通用表单——**前端不知道信源名** |
| ⑤ | `ctx.ingest`（有返回值） | 你要能感知「落地了没」：`{ok:true,id}` / `{ok:false,reason}`——**不抛**，失败自己决定重试或丢弃 |
| ⑥ | `ctx.reportError` | 无沙箱：错误报给 core 记入信源状态（`GET /api/sources` 的 `state/lastError/lastErrorAt`），不靠抛污染主进程 |
| ⑦ | `start?()` / `stop?()` | 注册（同步、无副作用）与启动（可异步可失败）分开；`stop` 收尾运行态（nc 在这里强制封批） |
| ⑧ | 宿主侧状态 | 你不用自己维护状态面板——`GET /api/sources` 给 `[{name, state, lastError?, lastErrorAt?, activity:[{label, at?}], guide?, settings}]`：`activity` 是**你自己在 `activity()` 里声明的信号**（按声明顺序，`at` 缺席 = 从未发生；保留键 `"ingest"` 由 core 自动打点并跨重启恢复）；`guide` 原样来自 `guide()`。core 与前端**不认识任何具体信号名**——加新源不需要改它们（D-115） |

**生命周期（三时机，D-88 核心；006 起按**空间**〔每账户〕各跑一次装配与启动）**：

| 时机 | 函数 | 谁调 | 你做什么 |
|---|---|---|---|
| ① 装配 core | `makeApp` | index + 测试 | （core 的事，与你无关——core 不知道信源存在） |
| ② 信源上岗 | `registerSources`（空间装配 hub 内） | core | 调你的 `register`：登记 webhook（`registrar`）、`ctx.setInterval` 起定时器 |
| ③ 信源启动 | `startSources`（空间装配 hub 内） | core | 调你的 `start?`：连外部、拉校验（可异步可失败） |

关闭路径：`SIGINT`（归 core，`index.ts` 统一 `process.on`）→ `app.close()` + 空间 `closeAll()` → 你的 `stop()` → 清理注册表反向撤销。

## 三、最小可运行骨架（复制就能改）

```ts
// apps/server/src/sources/mysrc/index.ts
import { z } from "zod";
import type { FastifyRequest, FastifyReply } from "fastify";
import type { ActivitySignal, SettingField, SourceAdapter, SourceContext, WebhookRegistrar } from "../types";

/** 我的源：一句话说明它收什么、怎么收。 */
export function makeMysrcAdapter(): SourceAdapter {
  return {
    name: "mysrc",

    /** 接收一条原始消息（Router 转发或本源的 hook 调）。解协议、算分组键、装 identity 都在这。 */
    accept({ raw, receivedAt }: { raw: unknown; receivedAt: string }) {
      const parsed = z.object({ text: z.string().min(1) }).safeParse(raw);
      if (!parsed.success) return { ok: false, reason: "消息形状不符" };
      // 单发源：直接投递；连发源：先缓冲（appendLine）再等四闸命中（dueStreams）后投递
      // receivedAt 供闸门用（**不要**拿它当 eventTime——01§5.3 禁接收时间兜底）
      return { ok: true };
    },

    register(ctx: SourceContext, registrar: WebhookRegistrar): void {
      // 登记 webhook（可达地址 = /hook/<账户令牌>/mysrc/event）；或用 ctx.setInterval 起轮询
      registrar.post("/event", async (req, reply) => {
        ctx.markActivity("event"); // 先打点再处理——命中即算「收到」，哪怕后面校验不过
        // 与 Router 走**同一个入口**（D-130）：hook 只负责收字节，解协议与分组都在 accept 里
        const result = this.accept({ raw: req.body, receivedAt: nowWallClock() });
        if (!result.ok) ctx.log.warn(`拒收：${result.reason}`); // 感知落地，失败自决重试/丢弃
        return reply.code(202).send();
      });
      // 定时器：ctx.setInterval 自动登记进清理表，core 关闭时撤销（不用自己 clearInterval）
    },

    settings(): SettingField[] {
      return [{ key: "endpoint", type: "text", label: "拉取地址", default: "https://…" }];
    },

    guide(): string {
      return "在我的源的「设置 → Webhook」里填下面的接入地址，勾选消息推送。";
    },

    activity(): ActivitySignal[] {
      return [
        { key: "event", label: "收到" }, // key 由你起名；label 是徽标上的短词
        { key: "poll", label: "拉取" },  // 声明顺序 = 展示顺序
      ];
    },
  };
}
```

```ts
// apps/server/src/sources/registry.ts —— 注册表加一个工厂（每空间各造一份实例）
const ADAPTER_FACTORIES: Array<() => SourceAdapter> = [makeNcAdapter, makeMysrcAdapter];
```

## 四、批次与元数据：你填什么、为什么

### ① 入口（唯一，别发明第二条）

一切进站走 `ctx.ingest(batch)`（或 HTTP `POST /api/ingest`，手动源用）。core 负责「先落盘（`raw_inputs`）后异步消化（agent0）」——LLM 挂了批次标「未处理」可重试，**原文永不丢**（01§5.3）。

### ② `source` 与 `identity`

- `source`：你的源的短名（= `name`），它是设置命名空间、路由前缀、排障标记（D-127 由 `sourceType` 改名）。
- `identity`：**弹性字典**——core 只约束「对象 + 保留键 `displayName` 非空」，其余键自由（QQ 填 `groupId`/`sender`，邮件填发件地址，网页填站点名）。整体 JSON 进 agent0 提示词——**你填的结构就是 agent0 的眼睛**（矛盾取舍、存疑库复原「同源接近度」都靠它）。
  - `displayName` = **给人看的文本来源**（区别于 id 类字段，D-127 由 `sourceLabel` 改名）；UI 只显示它。
  - ⚠️ **想让它参与矛盾取舍，就在身份里给可判定的字段**（角色、职务、官方标记都行）——只给一个「听起来像官方群」的名字，agent0 不会据此决断（D-127：无依据不得猜测）。
- `eventTime`：源自带时刻就填（比到达真实，相对日期按它锚定）；没有填 null。`receivedAt` core 自动记——两者差距本身是信息。

### ②b 单入口多流：照 `sources/wecom/batching.ts` 抄，不要自己发明一套

如果你的源**只有一个入口、但里面是很多条互不相干的对话/栏目**（企业微信客服是一个回调 URL 收所有客服账号+所有客户；
将来的新闻源是一个抓取入口收多个站点/栏目），照 `sources/wecom/batching.ts` 的三件套写一份：

- `KfLine`（= 你那份的行形状）：把协议字段映射成它（messageId / content / sender / senderId / at）。
- `KfBuffer` + `appendLine(buffers, key, displayName, line, seenAt)`：按**流键**分流累积。
- `dueStreams(buffers, nowMs, thresholds)`：四闸切段（静默 / 条数 / 字节 / 龄期，与 nc 同一套语义）。

⚠️ **这份件目前是 wecom 私有的，不是共享模块**（曾计划抽 `sources/batching.ts`，未落地）。
抄的时候保持一致；**改闸门语义要三处一起看**（nc / wecom / 你新抄的这份）——
两个副本已经各有一份，别造第三份还改出不同口径。

**你只需要回答一个问题：这条消息属于哪条流？**（nc 答 `group_id`/`user_id`；企业微信客服答 `open_kfid + external_userid`。）
`seenAt` 是**到达时刻**（不是消息自带时刻）——补推/拉取积压的旧消息不能把闸门带偏。

⚠️ **无法确定流键时不要猜**（不要挂到"最近一条流"上）：宁可丢一条并留痕，也不要把两个客户/两个栏目混进一批。

### ②c 私有媒体：实现 `fetchMedia`，别在正文里泄凭据

有些源的媒体**不是公开 URL**（企业微信只给 media_id，要带 access_token 才取得到字节）。
这种源实现可选的 `SourceAdapter.fetchMedia(placeholder)`：

- 正文里仍用全站统一的 `[图片](url)` 占位，url 段放你自己的**伪协议**（如 `wecom-media:<id>`）；
- **绝不把 access_token / secret 拼进正文**（原文会进提示词、导出、界面）；
- core 的图片缓存遇到非 http(s) 占位时，按批次的 `source` 查它登记的 `fetchMedia` —— 取不到只是这张图不缓存，
  正文里的占位逐字保留。

### ③ 打包（连发源才需要）

连发型源（QQ 群多块通知）在适配器内做**内存缓冲 + 切段封批**（D-127 四条件：静默满窗 / 攒够条数 / 攒够字节 / 距首条超时——任一命中即合并投递；阈值存设置）。**四条件缺一不可**：只按静默切，忙群一直有人说话就永不到期，批会无限涨、崩溃丢失也没上界。缓冲是信源私有内存态——core 不建表不恢复；崩溃丢失的上界由最快命中的那个条件决定，**要在文档里如实写这个上界**（别承诺一个忙群下不成立的窗口值）。封批决策写成**纯函数**（参照 nc 的 `dueGroups`/`assembleBatch`）便于测试。单发源（粘贴/邮件）拿到即 ingest。

**批次行协议（D-91，specs/003）**：多条合并时 `content` 逐行 `[HH:mm] 发送者（身份）: 正文`——跨天批次时刻升级 `[MM-DD HH:mm]`；角色小写归一后 owner/admin 显「群主/管理员」，member、缺席与未知值不显示（角色收宽松 string 且容 null，未知值不得丢事件）。三条硬规矩：**正文空白归一层面逐字保真**（协议字符只在行首；多行消息续行缩进两空格——引文校验按空白归一比对，不受影响）；**`identity.sender` 仅批内唯一发送者时写**，多人省略（发话人按 senderId 分辨，显示名会撞；任一事件缺 senderId 的多消息批次宁缺勿谎）；**守卫判消息正文**（行前缀会把全空批次衬成非空，全空批次照样丢弃）。两条已明确的边界：**显示名净化**（换行先折、半角 `: ` 换全角、剥「（群主）/（管理员）」字面量——顺序反了会重新造出分隔符）；**跨消息引文收紧**（行前缀插入非空白——旧版碰巧能过的「跨两条消息拼引文」现被围栏拒，更严格更正确，有 fence 断言）。**已接受残余风险**：消息正文本身无法消毒（逐字保真是硬约束）——成员可在正文伪造协议行，LLM 可能误读；勿以转义/消毒正文来「修」它（会断引文校验），此风险记录在案（D-91）。协议是信源侧约定，core/agent0 只当文本读、不做解析。

### ④ raw 归档（可选但推荐）

`ingest` 的 `SourceBatch` 多一个 `raw?: unknown`——塞进原始载荷（nc 原事件数组）。DB 落 `raw_inputs.raw` 列留底；shared 类型不含它（归档用，agent0/web 不消费）。

## 五、错误与边界约定（集中一处）

- **`ctx.ingest` 不抛**——判返回值 `.ok`。失败时**别记去重 id、别清缓冲**（否则该批消息既不落库又被去重吞掉，重推也丢）；留给下轮重试。
- **错误报 `ctx.reportError(err, {fatal?})`**，不靠抛——抛出去污染主进程。`start()` 抛错不用你管，core 只标记本信源 error。
- **白名单类过滤 fail-closed**：未配置 = 全不收（nc 的纪律——漏配不会把不该收的信息灌进来）。
- **快收语义**：webhook 入口一律快速 2xx（nc 用 204），校验不过静默丢——不阻塞推送方。
- **令牌鉴权归 core**：webhook 的令牌校验、401/404、日志脱敏由 core 网关统一处理——你只管协议本身（形状不符静默 204 照旧）。
- **SIGINT 不归你管**：core 统一 `process.on("SIGINT")` → `app.close()` → 你的 `stop()`。你只管在 `stop` 里收尾（如强制封批）。
- **红线：`ctx` 无 db**——信源不摸数据库；进站只经 `ctx.ingest`；core 不解释你的设置与载荷。
- **重推幂等你自己做**（nc 用 message_id 环形集合）——core 不替你去重。
- **删键 = 回「未设置」**：设置界面把数字输入清空即 `DELETE` 该键——你的 `getSetting` 兜默认值逻辑会被用户直接触发（约定出处在适配器侧，D-89 走查修订②）。

## 六、自测：怎么验证你的信源

1. **单测**（参照 `apps/server/src/test/nc.test.ts`）：
   - 纯函数单测（打包决策/规范化）；
   - 装配走 `apps/server/src/test/helpers/app.ts` 的 `makeTestAccount()`（真账户+真会话）；webhook 经 `/hook/<令牌>/<源名>/<路径>` 用 `app.inject` 打；
   - 封批触发用**只假 setInterval** 的假时钟（`vi.useFakeTimers({toFake:["setInterval","clearInterval"]})`——全量假时钟会让 `app.inject` 挂死）；⚠️ 必须在**空间装配（`ensure`）之前**调，否则假时钟接管不到信源的定时器，`advanceTimersByTime` 推不动；
   - 走真实断言：`repo.listRawInputsByState(db, "digested")` 出现你的批次。
2. **全链路手测**（最小验收链）：真实事件 → 入口 2xx → `raw_inputs` 落档（pending→digested）→ 看板出事项 → 点开可溯源到本批次原文。
3. **联调**：设置经 `PUT /api/sources/<名>/settings/<键>` 热改（或等前端按 schema 渲染的表单）；日志看 stderr 的 `[source:<名>]` 前缀。
4. **展示信息自检**：`GET /api/sources` 里你的源应带 `activity: [{label, at?}]`（按 `activity()` 声明顺序）与 `guide`；触发一次你打点的时机 → 对应 `at` 变化。打点了未声明的 key 会在 stderr 看到「未声明的活动信号」并忽略——那是拼错了，不是 core 的 bug。
