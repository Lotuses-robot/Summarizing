# 07 · 信源开发指南（D-88 定稿；样板源 = chat，参照实现 = nc）

> **本文件 = 「接入一个新信源」的唯一说明书**。上游：D-84（信源化源架构）、D-85（存疑库）、D-88（契约重设计八件套）。
> **验收锚点（唯一硬指标）：照本指南能独立写出一个新信源**（04§五：掐表 ≤ 30 分钟为达标）。
> 参照物：样板源 chat（`application/chat.ts` 的 ingest 工具，无适配器）；**唯一完整适配器 = nc**（`apps/server/src/sources/nc/`）。

---

## 一、30 秒总览：信源是什么、不是什么

- **信源 = 源适配器**：一个源一个目录（`apps/server/src/sources/<源名>/`），实现 `SourceAdapter` 接口、注册表（`sources/registry.ts`）加一行。core 不感知你的协议，**core 装配（`makeApp`）甚至不知道有哪些信源**。
- **变数全留给你**：解释协议、打包（要不要合并碎片）、管设置——都是你自己的事；core 只提供「手段」（`SourceContext`）与「场地」（Fastify 路由挂载权）。
- **「信源」≠「插件」**（D-88 术语定稿）：插件 = 未来更大的扩展体系（信源将是它的子类）。本指南只讲信源。
- **不是**：不做 manifest、不做运行时加载/沙箱、不做依赖编排、不做自动发现（D-88「明确不要」清单）。

## 二、契约：`SourceAdapter` 与八件套（完整签名）

> 单一来源：`apps/server/src/sources/types.ts`（本文照抄，改契约先改那里再改这里）。

```ts
/** 信源适配器：一个源一个目录，实现本接口、注册表加一行。 */
export interface SourceAdapter {
  /** 源的唯一短名——sourceType、信源设置命名空间、from 排障标记共用。 */
  readonly name: string;
  /** 上岗（装配期，同步）：挂路由、起定时器、存引用——不阻塞、不连外部。 */
  register(ctx: SourceContext, app: FastifyInstance): void;
  /** 启动（可选）：可异步、可失败。失败只标记本信源 error，不拖垮别的。nc 就不需要写。 */
  start?(): void | Promise<void>;
  /** 停止（可选）：清自己的运行态（如强制封批缓冲）。core 关闭时调用。 */
  stop?(): Promise<void>;
  /** 声明设置项（纯数据）。缺席 = 无设置。core 落库并随 GET /api/sources 吐给前端。 */
  settings?(): SettingField[];
}

/** core 交给信源的手段（八件套）。刻意无 db——信源不摸数据库。 */
export interface SourceContext {
  readonly name: string;                                                    // ② 自我标识
  ingest(batch: SourceBatch): { ok: true; id: string } | { ok: false; reason: string }; // ⑤ 投递口
  getSetting(key: string): unknown;                                         // 设置读写（命名空间隔离）
  setSetting(key: string, value: unknown): void;
  log: { debug(msg: string): void; info(msg: string): void; warn(msg: string): void; error(msg: string): void }; // ① 日志口（core 加前缀）
  onCleanup(fn: () => void | Promise<void>): void;                          // ③ 清理注册表
  setInterval(fn: () => void, ms: number): void;                            // 定时器助手（自动登记；core 关闭时统一撤销）
  reportError(err: unknown, opts?: { fatal?: boolean }): void;              // ⑥ 错误出口
}
// SettingField 六型：text / number / boolean / select / record / secret（key/type/label/description?；default? 仅 text/number/boolean/select/secret 有，record 无）
```

**八件套每件的「为什么」**（业界依据见 `docs/10` §T0；HA / VS Code / Telegraf / Obsidian 横向对比）：

| # | 手段 | 为什么存在 |
|---|------|-----------|
| ① | `ctx.log` | 你不该自己写 `process.stderr`——core 统一加 `[source:<名>]` 前缀，日志可按源过滤 |
| ② | `ctx.name` | 日志前缀 / 设置命名空间 / 错误归属共用，你不用自己再定义常量 |
| ③ | `ctx.onCleanup` | 一个信源有多个资源（定时器+监听器+socket），core 关闭时按**单源内后注册先撤销**逐项清理；返回单个清理函数容不下 |
| ④ | `settings()` + `ctx.get/setSetting` | 设置项声明成**纯数据**（六型），core 落库 `__schema__`，前端按 schema 渲染通用表单——**前端不知道信源名** |
| ⑤ | `ctx.ingest`（有返回值） | 你要能感知「落地了没」：`{ok:true,id}` / `{ok:false,reason}`——**不抛**，失败自己决定重试或丢弃 |
| ⑥ | `ctx.reportError` | 无沙箱：错误报给 core 记入信源状态（`GET /api/sources` 的 `state/lastError`），不靠抛污染主进程 |
| ⑦ | `start?()` / `stop?()` | 注册（同步、无副作用）与启动（可异步可失败）分开；`stop` 收尾运行态（nc 在这里强制封批） |
| ⑧ | 宿主侧状态 | 你不用自己维护状态面板——`GET /api/sources` 给 `[{name, state, lastError?, lastOkAt?, settings}]` |

**生命周期（三时机，D-88 核心）**：

| 时机 | 函数 | 谁调 | 你做什么 |
|---|---|---|---|
| ① 装配 core | `makeApp` | index + 测试 | （core 的事，与你无关——core 不知道信源存在） |
| ② 信源上岗 | `registerSources` | **只有 index** | 调你的 `register`：挂路由、`ctx.setInterval` 起定时器 |
| ③ 信源启动 | `startSources` | **只有 index** | 调你的 `start?`：连外部、拉校验（可异步可失败） |

关闭路径：`SIGINT`（归 core，`index.ts` 统一 `process.on`）→ `app.close()` → 你的 `stop()` → 清理注册表反向撤销。

## 三、最小可运行骨架（复制就能改）

```ts
// apps/server/src/sources/mysrc/index.ts
import { z } from "zod";
import type { FastifyInstance } from "fastify";
import type { SettingField, SourceAdapter, SourceContext } from "../types";

/** 我的源：一句话说明它收什么、怎么收。 */
export function makeMysrcAdapter(): SourceAdapter {
  return {
    name: "mysrc",

    register(ctx: SourceContext, app: FastifyInstance): void {
      // 挂自己的路由（/api/sources/mysrc/...）或用 ctx.setInterval 起轮询
      app.post("/api/sources/mysrc/event", async (req, reply) => {
        const body = z.object({ text: z.string().min(1) }).parse(req.body);
        // 单发源直接投递；连发源自己缓冲 + 去抖封批（参照 nc 的 dueGroups/assembleBatch 纯函数）
        const result = ctx.ingest({
          content: body.text,
          sourceType: "mysrc",
          sourceIdentity: { sourceLabel: "我的源" }, // 保留键 sourceLabel 非空；其余键自由
          eventTime: null, // 自带时刻就填（本地墙钟格式）
        });
        if (!result.ok) ctx.log.warn(`投递失败：${result.reason}`); // 感知落地，失败自决重试/丢弃
        return reply.code(202).send();
      });
      // 定时器：ctx.setInterval 自动登记进清理表，core 关闭时撤销（不用自己 clearInterval）
    },

    settings(): SettingField[] {
      return [{ key: "endpoint", type: "text", label: "拉取地址", default: "https://…" }];
    },
  };
}
```

```ts
// apps/server/src/sources/registry.ts —— 注册表加一行
const ADAPTERS: SourceAdapter[] = [makeNcAdapter(), makeMysrcAdapter()];
```

就这些。`index.ts` 的三步装配、`GET /api/sources`、设置读写、状态表——全部自动生效。

## 四、批次与元数据：你填什么、为什么

### ① 入口（唯一，别发明第二条）

一切进站走 `ctx.ingest(batch)`（或 HTTP `POST /api/ingest`，手动源用）。core 负责「先落盘（`raw_inputs`）后异步消化（agent0）」——LLM 挂了批次标「未处理」可重试，**原文永不丢**（01§5.3）。

### ② `sourceType` 与 `sourceIdentity`

- `sourceType`：你的源的短名（= `name`），它是设置命名空间、路由前缀、排障标记。
- `sourceIdentity`：**弹性字典**——core 只约束「对象 + 保留键 `sourceLabel` 非空」，其余键自由（QQ 填 `groupId`/`sender`，邮件填发件地址，网页填站点名）。整体 JSON 进 agent0 提示词——**你填的结构就是 agent0 的眼睛**（矛盾取舍「谁更官方」、存疑库复原「同源接近度」都靠它）。
  - `sourceLabel` = **给人看的文本来源**（区别于 id 类字段）；UI 只显示它。
- `eventTime`：源自带时刻就填（比到达真实，相对日期按它锚定）；没有填 null。`receivedAt` core 自动记——两者差距本身是信息。

### ③ 打包（连发源才需要）

连发型源（QQ 群多块通知）在适配器内做**内存缓冲 + 去抖封批**（组内静默 ≥ 窗口才合并投递；窗长存设置）。缓冲是信源私有内存态——core 不建表不恢复（崩溃丢 ≤1 窗口，源里还有）。封批决策写成**纯函数**（参照 nc 的 `dueGroups`/`assembleBatch`）便于测试。单发源（粘贴/邮件）拿到即 ingest。

**批次行协议（D-91，specs/003）**：多条合并时 `content` 逐行 `[HH:mm] 发送者（身份）: 正文`——跨天批次时刻升级 `[MM-DD HH:mm]`；角色小写归一后 owner/admin 显「群主/管理员」，member、缺席与未知值不显示（角色收宽松 string 且容 null，未知值不得丢事件）。三条硬规矩：**正文空白归一层面逐字保真**（协议字符只在行首；多行消息续行缩进两空格——引文校验按空白归一比对，不受影响）；**`sourceIdentity.sender` 仅批内唯一发送者时写**，多人省略（发话人按 senderId 分辨，显示名会撞；任一事件缺 senderId 的多消息批次宁缺勿谎）；**守卫判消息正文**（行前缀会把全空批次衬成非空，全空批次照样丢弃）。两条已明确的边界：**显示名净化**（换行先折、半角 `: ` 换全角、剥「（群主）/（管理员）」字面量——顺序反了会重新造出分隔符）；**跨消息引文收紧**（行前缀插入非空白——旧版碰巧能过的「跨两条消息拼引文」现被围栏拒，更严格更正确，有 fence 断言）。**已接受残余风险**：消息正文本身无法消毒（逐字保真是硬约束）——成员可在正文伪造协议行，LLM 可能误读；勿以转义/消毒正文来「修」它（会断引文校验），此风险记录在案（D-91）。协议是信源侧约定，core/agent0 只当文本读、不做解析。

### ④ raw 归档（可选但推荐）

`ingest` 的 `SourceBatch` 多一个 `raw?: unknown`——塞进原始载荷（nc 原事件数组）。DB 落 `raw_inputs.raw` 列留底；shared 类型不含它（归档用，agent0/web 不消费）。

## 五、错误与边界约定（集中一处）

- **`ctx.ingest` 不抛**——判返回值 `.ok`。失败时**别记去重 id、别清缓冲**（否则该批消息既不落库又被去重吞掉，重推也丢）；留给下轮重试。
- **错误报 `ctx.reportError(err, {fatal?})`**，不靠抛——抛出去污染主进程。`start()` 抛错不用你管，core 只标记本信源 error。
- **白名单类过滤 fail-closed**：未配置 = 全不收（nc 的纪律——漏配不会把不该收的信息灌进来）。
- **快收语义**：webhook 入口一律快速 2xx（nc 用 204），校验不过静默丢——不阻塞推送方。
- **SIGINT 不归你管**：core 统一 `process.on("SIGINT")` → `app.close()` → 你的 `stop()`。你只管在 `stop` 里收尾（如强制封批）。
- **红线：`ctx` 无 db**——信源不摸数据库；进站只经 `ctx.ingest`；core 不解释你的设置与载荷。
- **重推幂等你自己做**（nc 用 message_id 环形集合）——core 不替你去重。
- **删键 = 回「未设置」**：设置界面把数字输入清空即 `DELETE` 该键——你的 `getSetting` 兜默认值逻辑会被用户直接触发（约定出处在适配器侧，D-89 走查修订②）。

## 六、自测：怎么验证你的信源

1. **单测**（参照 `apps/server/src/test/nc.test.ts`）：
   - 纯函数单测（打包决策/规范化）；
   - `makeApp({db, llmRef})` + `registerSources(app, deps, [adapter])` 两步装配，`app.inject` 打你的路由；
   - 封批触发用**只假 setInterval** 的假时钟（`vi.useFakeTimers({toFake:["setInterval","clearInterval"]})`——全量假时钟会让 `app.inject` 挂死）；⚠️ 必须在 `registerSources` **之前**调，否则假时钟接管不到信源的定时器，`advanceTimersByTime` 推不动；
   - 走真实断言：`repo.listRawInputsByState(db, "digested")` 出现你的批次。
2. **全链路手测**（最小验收链）：真实事件 → 入口 2xx → `raw_inputs` 落档（pending→digested）→ 看板出事项 → 点开可溯源到本批次原文。
3. **联调**：设置经 `PUT /api/sources/<名>/settings/<键>` 热改（或等前端按 schema 渲染的表单）；日志看 stderr 的 `[source:<名>]` 前缀。
