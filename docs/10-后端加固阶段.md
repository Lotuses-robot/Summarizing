## 一、为什么先做这个（用户 2026-09-29 定）

原计划「信源阶段 → UI 收口 → 测试使用 → 知识库」。讨论中发现：**UI 收口里有一半待办其实是「信源契约」**，且与 UI 的验收标准完全不同（UI 看观感/交互，信源契约看「能不能照着写出来」）。故：

## 二、本阶段任务清单（2026-09-29 讨论逐条定稿）

### T0 · 插件契约审慎重设计（**最高优先**——2026-09-29 用户：「感觉做的好草率——插件这一部分的实现要好好审视一下」）

**诊断**（审视 `apps/server/src/sources/types.ts` 全部 30 行后）：

| # | 缺陷 | 说明 |
|---|------|------|
| P1 | **`sweep()` 是 nc 的形状泄漏** | 「去抖封批」只是 nc 的实现细节（chat/paste/未来 RSS 都不需要），却被硬塞进通用接口 → **每个插件都得实现一个对自己无意义的方法**（替身源只好 `sweep: () => 0`）。**这是「接新源成本」的直接敌人**。**已定：从接口移除**（用户 2026-09-29） |
| P2 | **`sweep()` 没有 core 侧调用者** | 注释说「SIGINT + 测试用」，但 SIGINT 归插件自己处理 → 一个接口方法「只给自己用」= 不该在接口上 |
| P3 | **生命周期未定义** | ① `register` 返回清理函数，但状态在构造闭包——`sweep()` 在 register 前调用静默返回 0；② **一个实例 register 两次会怎样？**（runtime 覆盖、定时器/监听器叠加）接口没规定 |
| P4 | **`SourceContext` 缺插件真正需要的** | 无日志口（只能 `process.stderr.write`）、无自我标识（只能自己写常量，`NC_SOURCE_NAME` 就是为此而生）、无设置 schema 声明、无清理注册、无 state 端点（D-84 声称的「core 三手段」之一，从未实现） |
| P5 | **错误语义空白** | `ingest(batch): void` —— **实际会抛**（`app.ts:44` 的 `IngestRequestSchema.parse` + `insertRawInput`），但返回类型 `void` 完全没表达。插件作者不会知道要 try/catch（nc 是自己摸索出来加的）。**契约没说「抛了怎么办」** |
| P6 | **「插件」概念未澄清** | D-84 全程说的是「源适配器」；「插件」一词被混用。**用户 2026-09-29 澄清：「我的说法说错了，就是信源」**——插件 = 信源接入，不做通用扩展体系；契约定为**小而精，只服务信源** |
| P7 | **无「已注册」防护**（P3 实证） | `app.ts:131` 的注册循环无任何检查——同一 adapter 实例 `register` 两次 → `runtime` 覆盖、定时器/SIGINT 监听器叠加。契约无防护、core 无检查 |

**已定的契约修订**（用户 2026-09-29 逐条确认）：
- ❌ **移除 `sweep()`**——打包是插件内部事，core 不需要知道
- ✅ `SourceContext` 增：**日志口**（`ctx.log`，core 统一收集/前缀，替代直接写 stderr）、**自我标识**（`ctx.name`）、**设置声明**（`ctx.defineSettings`）、**清理注册**（`ctx.onCleanup`，替代 register 返回值）
- ⏳ **待调研补充**：用户「我没做过类似的项目，你再找找会不会还有什么需要的？」

**业界调研结论（2026-09-29，参照 HA / VS Code / Telegraf / Logstash / Obsidian / Nuxt / Gatsby / Sentry）**：

> 一句话：**「日志 + 自我标识 + 清理注册表 + 代码内设置 schema + 投递口 + 错误出口 + start/dispose 两钩子 + 宿主侧插件状态」是必备八件；manifest/贡献点/发现/依赖编排/flow 向导全部明确不要。**

关键横向结论（各家一致的）：
- **清理注册表 > 返回清理函数**：HA `async_on_unload` / VS Code `subscriptions` / Obsidian `register*` 三家同构——**一个插件注册多个资源、后注册先撤销**。我们现「返回单个函数」容不下（定时器 + 监听器 + 路由 + 未来的 socket）。
- **设置 schema 走「代码内声明式纯数据」**（Obsidian `getSettingDefinitions()` 派）：插件返回一个 `SettingField[]` 数组（`key/type/label/default/description`，`type ∈ text|number|boolean|select|secret`），core 原样吐给前端渲染。**不做** manifest 文件、**不做** HA 那种多步 flow 向导（我们单进程、无沙箱、设置项个位数）。
- **无沙箱 ⇒ 错误必须由 core 在插件边界兜底**（Telegraf `acc.AddError` 模式）——插件抛错不能污染主进程；`ctx.reportError(err, {fatal?})` + 宿主记录 `{state: ok|degraded|error, lastError, lastOkAt}`。
- **`ingest` 应给返回值**（接受情况/reject 原因）——否则插件**感知不到自己的数据有没有落地**（Telegraf tracking 模式）。
- **`register` 拆开**：注册（无副作用/不阻塞）vs `start()`（可异步、可失败）——启动失败要在 start 暴露，宿主**只标记该插件 error，不拖垮其它插件**。
- **定时器助手** `ctx.setInterval/setTimeout`（自动登记进清理表）——正是 nc 现在的痛点。

**必备八件（定稿）**：①日志口 `ctx.log` ②自我标识 `ctx.name` ③清理注册表 `ctx.onCleanup` ④代码内设置 schema ⑤投递口 `ctx.ingest`（给返回值）⑥错误出口 `ctx.reportError` ⑦`start()`/`dispose()` 两钩子 ⑧宿主侧插件状态 `{state, lastError, lastOkAt}`

**可选（有余力再加）**：能力声明（可选接口/布尔，如 `manual?: true`/`hasSettings?: true`）· 健康/心跳 `health()`（前端显示「nc 已 5 分钟无消息」）· 敏感值 `type:'secret'`（不明文回显）· 设置数据版本迁移 `settingsVersion + migrateSettings` · 单向通知 `ctx.emit` · 定时器助手

**明确不要**（业界有但我们用不上）：manifest 文件/声明式贡献点清单 · config flow 多步向导/OAuth/reauth · 依赖声明与拓扑加载 · 自动发现（zeroconf/ssdp/bluetooth） · 版本兼容协商/热加载/动态加载/沙箱/fork 隔离 · 状态持久化 API（我们「插件不摸数据库」） · 自动指数退避重试（降级 + 用户手动重启更简单）

**当前契约的两个真缺口**（其余是补齐）：**清理注册表**、**设置 schema 声明**。

## 五、定稿补遗（2026-09-29 深聊，覆盖上文 §三/§四/§六 的早期假设）

> ⚠️ 本节 = **最终定稿**；上文 §三（UI 收口待办）仍有效，但 §四/§五/§六 的早期假设以本节为准。完整施工计划见 `~/.claude/plans/fuzzy-riding-kurzweil.md`（plan 模式产出）。

### 5.1 契约最终形状（必备 + 可选）

```ts
// core 交给信源的「手段」
interface SourceContext {
  readonly name: string;                              // 自我标识
  ingest(batch): { ok: true; id: string } | { ok: false; reason: string };  // 给返回值（能感知落地）
  getSetting(key): unknown; setSetting(key, value): void;                    // 设置读写（命名空间隔离）
  log: { debug/info/warn/error(msg): void };          // 日志口（core 加 [source:name] 前缀）
  onCleanup(fn): void;                                // 清理注册表（容多资源）
  setInterval(fn, ms): void;                          // 定时器助手（自动登记；施工后 review 收紧：句柄无调用者，纪律 #4）
  reportError(err, {fatal?}): void;                   // 错误出口（无沙箱，不靠抛）
}

// 信源实现
interface SourceAdapter {
  readonly name: string;
  register(ctx, app): void;              // 装配期：挂路由/起定时器（同步）
  start?(): void | Promise<void>;        // 启动期（可选！异步信源才写；nc 不写）
  stop?(): Promise<void>;                // 停止（可选）
  settings?(): SettingField[];           // 声明设置项（纯数据）
}
// SettingField 六种：text / number / boolean / select / record / secret
```

### 5.2 三时机分离（**核心架构决定**）

| | `makeApp`（装配 core） | `registerSources`（信源上岗） | `startSources`（信源启动） |
|---|---|---|---|
| 干什么 | core 自己的路由 | 信源挂自己的路由 | 信源真正开始工作 |
| 同步/异步 | 同步 | 同步 | **可异步** |
| 谁调 | **index + 测试** | **只有 index** | **只有 index** |
| 知道信源吗 | **完全不**（无 sources 参数） | 是 | 是 |

**关键**：core 装配**不知道信源存在**（呼应「前端不该知道有什么信源」）。测试只调 `makeApp`（更纯），测信源走 `registerSources`。

### 5.3 SIGINT 归 core（修正信源阶段的「有意不修」）

`index.ts` 装配处统一 `process.on("SIGINT", async () => { await app.close(); process.exit(0); })`——`app.close()` 触发所有信源的 `stop` + 清理注册表。**信源不再自己 `process.on`**。

### 5.4 版本来源：**信源只挂证据，版本不存来源**

- `ItemVersion.by`：字符串 → **`{ actor: string; model: string | null }`**（actor 自由字符串）
- **信源不存版本上**——需要时走证据链（版本→证据→片段→批次→`sourceIdentity`）
- **砍掉**：~~版本 source 字段~~ ~~来源名统一接口~~（信源只在证据，无第二个来源概念）

### 5.5 保留键改名 `name` → `sourceLabel`

弹性字典保留键（现 `name`）改为 **`sourceLabel`**——明确是「给人看的文本来源」，区别于 `groupId` 类 id 字段。UI 只显示它。

### 5.6 术语全面改名：「插件 → 信源」（用户 2026-09-29 强调「必须要改」；施工**第 0 步**）

用户：「为 plugin 留出语义——以后说不定可以做个插件生态」。**信源 = 源适配器；「插件」留给未来更大的扩展体系**。
- 表 `plugin_settings` → `source_settings`（`ALTER TABLE RENAME TO`）+ **列名 `plugin` → `source`**（`RENAME COLUMN`，RENAME TO 不改列名——2026-09-29 施工时由迁移测试抓出）
- `routes/plugins.ts` → `routes/sources.ts`；`/api/plugins/*` → `/api/sources/*`
- 变量/注释/文档全改（保留 `docs/10` 里「插件生态」的**未来**语境）
