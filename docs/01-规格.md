## 一、防复发纪律（最高优先级）

前身项目死于范围失控：做了一大堆处理能力，但没有一条真实信息流过完整闭环。因此本项目遵守：

| # | 纪律 | 判据 |
|---|------|------|
| 1 | **先跑通一次完整业务循环，再谈任何扩展** | 一条真实信息从录入走到看板可见、证据可查，中间不断链 |
| 2 | **每个阶段结束时系统必须可独立使用** | 不允许「等全做完才能用」 |
| 3 | **模块数量受控** | 用户必须能看懂、改得动。宁可功能少，不可结构乱 |
| 4 | **不写没有调用者的东西** | 「谁调它？」答不上来就删掉。标注「未接线」不算免责 |
| 5 | **验证必须独立于被验证的东西** | 在真实入口验证，断言用户看到的那行字，不只测内部函数 |
| 6 | **遇到不确定的设计选择，先问，不要自己发挥** | 用户失去掌控力是弃项目的直接原因 |

## 二、项目画像

- **用户**：P0 = 用户本人（在校学生，有大量课程作业与社团事务）。P1 = 其他信息过载的人，暂不为其做任何妥协。
- **部署**：本地运行，桌面端为主。**不做**手机 App、多端同步、云端、多用户。
- **核心问题**：「永远不确定自己是不是漏了」的持续焦虑 + 「你不知道自己不知道」的盲区。不是"信息太多"，而是片段分散多处拼不出全貌，以及**沉默的失败**（根本没进入认知）。

### 成功判据

| # | 判据 | 说明 |
|---|------|------|
| 1 | ⭐ **敢不看** | 可以连续几天不翻那些源而不焦虑。**唯一的有效验证** |
| 2 | **零不可逆遗漏事故** | 没有因遗漏导致不可逆后果 |
| 3 | ⭐ **不制造新噪声** | 给出的每一条都值得看 |
| 4 | **可追溯** | 任何结论都能低成本回溯到原始出处 |
| 5 | **开箱即用** | 不要求用户先做前置配置 |

### 被禁止的失败形态

| 形态 | 为什么致命 |
|------|-----------|
| **静默失效**（狼来了） | 误推几次后用户无视一切 → 系统表面在跑，实际已失效 |
| **第 N+1 个窗口** | 用户又开始刷这个工具，焦虑不减反增 |

## 三、MVP 场景：E（追踪遗漏）

| 场景 | 失败模式 | 频率 | MVP |
|------|----------|------|-----|
| A 截止日期型 | 片段散落，材料与入口没凑齐 | 中 | 间接覆盖（§6.5） |
| B 低频不可逆型 | 通知淹在高频闲聊里没看见 | 低 | ❌ 最害怕但不先做：几个月没反馈、需自动采集、需调优 |
| C 静态知识盲区型 | 规则埋在文档深处，不知道它存在 | 常见但不可感知 | 经 §4.9 / §4.1 间接处理，不做独立知识库界面 |
| D 灵感速记型 | 想法没捕获或检索不到 | 中 | ❌ 不在 MVP |
| **E 追踪遗漏型** | 信息**被感知到了**，但从未变成"被追踪" | **高** | ✅ **选定** |

**选 E 不选 B 的理由：恐惧不是选择 MVP 的标准，反馈频率才是。** E 高频、几天就能验证一次闭环；B 做完要等几个月才知道有没有用——那正是前身项目失去动力的死法。

### 两个真实案例（需求的唯一事实来源）

**案例 1 · 课后作业追踪丢失**：老师口头提了一句 → 用户当下判断「肯定会记得」→ 这个判断错了且当下无法知道它错了 → 靠问舍友才发现，已临近下次课。断点在「听到 → 记下」之间的约 30 秒；障碍不是操作成本，是**信心偏差让操作显得没必要**。

**案例 2 · DDL 字段张冠李戴**：信息就在眼前，失败发生在**理解**环节——把 A 的截止日期读成了 B 的。⚠️ 自动采集对此**完全无效**。

### 由此得出的最重要结论

> **两个真实案例都不是采集失败，都是处理失败。MVP 绝不能做成"信息采集项目"。**
> 实施中任何"要不要先加个采集器"的提议，都拿这条对照。

## 四、核心设计

### 一件事情的去处（总览）

**看板 = 一个列表，按「确定程度」分四段，从上到下越来越确定；拿不准的信息进存疑信息库（§4.12）；搁置隐身名单 ⏸️ 延后（L-17）；另有内部进料口（待处理队列）。**（D-39 状态制 → D-80 五段 → D-85 存疑信息库 → D-89 存疑段退场、四段定稿）

```
事情确认存在了吗？系统能自己处理吗？
├─ 没确认 / 系统打平无法取舍           → 存疑信息库（§4.12，D-85；不进看板）
├─ 确认了，日期没有                    → 日期未知
├─ 确认了，有日期                      → 已排期（按 ddl 排序）
└─ 确认了，只是某个字段缺               → 空位（事项上的空字段，不是一行）

用户主动说"不追了"                     → 搁置（⏸️ 延后 L-17）
目标明确的修改/补充                     → 直接应用（Replay 节点）
目标不明的修改指令                      → 不应用、不追问；原话入存疑信息库（§4.12，D-85）
```

| 去处 | 装什么 | 谁放进去 | 在哪看到 | 怎么离开 |
|------|--------|----------|----------|----------|
| **日期未知** | 确认存在 + 没日期 | agent0 | 看板第一段 | 日期数据到达 → 自动移入已排期 |
| **已排期** | 确认存在 + 有日期 | agent0 | 第二段，按 ddl 排 | 标完成；过期如实展示（§4.15） |
| **搁置**（⏸️ 延后 L-17） | 用户主动放弃追踪 | **用户**（一次点击） | 不在看板，安静躺着 | 切确信息命中 → agent0 主动提起回看板；用户确认了结 → 归档 |
| **归档**（终态） | 了结的事项（搁置了结，或用户对活跃事项直接归档——D-83） | 用户确认 | 看板末段（D-83 最小归档已启用） | 不再离开（不删除，不进 agent0 上下文） |
| 待处理队列 | 已粘贴、未消化的原始文本 | 前台（ingest） | 不在看板（处理进料口） | agent0 消化（§5.3） |
| 空位 | 事项上缺的字段 | — | 事项详情页 | 数据到达静默填充 |
| ~~存疑段~~（D-89 退场） | ~~存量存疑事项~~ 存量已解除（D-89）；`doubtNote` 字段与 `resolve_doubt` 词表保留仅作数据留痕，无 UI | — | — | — |

⭐ 看板四段互斥（§4.12 / §4.13；D-80 五段定稿 → D-89 四段）：**日期未知 = 缺日期；已排期 = 有日期；已完成 = 用户已处置；已归档 = 已了结（D-83 最小归档已启用）。** 搁置仍在看板之外（缺意愿；⏸️ 延后 L-17）。段序 = 确定程度递增。拿不准的信息进**存疑信息库**（§4.12，独立审核页 D-89），不以存疑事项形态占看板。
⭐ **前台是统一修订入口**：解决存疑、修正事项、补充信息，都是对前台说一句话，由 agent0 落节点——不需要任何专门的"处理队列"界面。

### 4.1 数据模型：事项（单一节点）+ 标签

> ⚠️ **2026-09-25 模型重构**：原「任务树 + 事项」两层模型废弃（任务退场、改为标签）。**数据层的精确契约见 `00-数据契约.md`（权威）**；本节是规格层的摘要。

```
事项 (Item)                          ← 唯一节点，看板的一行
  ├─ elements[]                      ← 内容，全是元素（全元素化）
  │    ├─ 固定元素：name（语义名，禁裸日期）/ dueDate（本地墙钟，D-64）/ summary（D-65）
  │    └─ 自由元素：label 自拟（链接/地点/材料…），text 一句人话
  ├─ tags[]                          ← 归类标签（独立字段，不是元素、不挂证据）
  ├─ status：todo | done | archived   ← 处置状态（独立字段；archived 已启用 D-83，仅 shelved 预留）
  └─ doubtNote                       ← 存疑标记（独立字段；⚠️ D-85 起停新增——agent0 拿不准改入存疑信息库；D-89 起 UI 全退场，字段仅数据留痕）
        │
        └─ 元素 ──依据──→ 原文快照 / 知识（单向）
```

- **事项必须自带语义名**（固定元素 `name`，禁裸日期）——张冠李戴因此在**结构上不可能**发生（事前预防，强于事后发现）。
- **没有任务树、没有嵌套、没有面包屑**（原父子结构退场）。归类靠 `tags`：一个事项多个标签、可空、不强制。
- **子链接不作为第三类边**：S1 无父子；`tags` 与「事项↔标签」是同一层（详情见 00-数据契约 §三）。
- **知识不存在事项里**：存储独立（§4.9），呈现时由 agent0 组装到事项详情页。
- **元素**（D-63 + 2026-09-25 全元素化）：事项的**唯一内容载体**。固定元素（`name`/`dueDate`/`summary`）与自由元素**同一类型**（根本类型 + `extend` 衍生），区别只在规则表。标签「链接」「地点」等由 agent0 自主提取；用户可在前台对话中补充（D-60）。UI 在「基本信息」区渲染固定元素，自由元素在其下，各自展开证据链。
- **详细说明**（固定元素 `summary`，D-65；**2026-09-29 修订**）：**主干一句话**——说清「这是件什么事」（谁的事、要做什么），让用户扫一眼明白大概；**具体细节（时间/入口/材料/要求/注意事项）不写这里**，它们在下方信息元素中更有条理地罗列。判据：summary 出现「XX 平台」「须以…为单位」「截止…」「入口…」即写多了（与元素重复）。
- 用户不需要知道某条知识存在；打开事项，系统已把上下文组装好。检索式问答是**次要**能力。❌ 不做独立知识库浏览界面作为主要入口。

### 4.2 「未知」的处理：空位或自己的位置，绝不借用别人的日期

**判据只有一句：这个未知有没有一个「已被追踪的主人」？**

| 情况 | 有主人吗 | 去处 |
|------|----------|------|
| 报名链接未知 | ✅ 属于已追踪的"报名截止"事项 | **空位**——打开事项自然看见 |
| 事项日期本身未知 | ✅ 事项已确认存在，但无法排序 | **日期未知段**（§4.3） |
| "听说要加口语考试" | ❌ 事情本身未确认 | **存疑**（§4.12） |
| "这两条是不是同一件事" | ❌ 悬空的判断 | **存疑**（附候选注记，§4.12） |

- 空位 = 事项上的**空字段**，不是独立实体、不是队列行。
- 数据到达时**静默填充**。⚠️ 「静默」只修饰**输入侧**（无需用户操作）；处理侧**固定元素一项不少**（事后可核查），判不了照常走各自降级路径（存疑 / 留空位 / 日期未知段）。
- ❌ **禁止任何形式的日期继承/传播**（父、兄弟、任何来源）。一个错误的日期比没有日期危险得多：没有你会去查，错误的你会直接信。
- ❌ 禁止把未知字段做成队列行（噪声爆炸）。
- 区分：**字段未知**（有日期，正常排序）vs **日期本身未知**（无法排序 → 日期未知段）。

### 4.3 排序与看板（状态制，四段；D-80 五段 → D-89 四段）

- **看板是一个列表**，按确定程度分四段：**日期未知 → 已排期 → 已完成 → 已归档**。已完成/已归档默认折叠；归档 = 用户直接归档（D-83 最小归档已启用）；搁置流 ⏸️ 延后（L-17，用户 2026-09-28：暂时不需要）。没有第二个视图，没有独立分区。~~存疑段~~ 已随 D-89 退场（拿不准一律进存疑信息库 §4.12，独立审核页）。
- **看板行布局（D-80；用户 2026-09-27 定稿 v3，借鉴 Todoist/Things 3）**：行上放**标题 → 相对人话 ddl → tags 内联**（同一阅读线，不右缘远跳）；ddl 颜色编码（过期红/临近强调/远灰），绝对时间悬停可见；**过期行 = 淡红底 + 行内时间字标红**（用户 2026-09-27 简化：去框留底，轻量提示；替代 D-34 的最小描边）；**推断 = 左缘内缩状态条**（灰蓝，悬停给全文；状态标记不做读目标）。推断说明等细节仍看展开详情。~~存疑琥珀条~~ 已随 D-89 退场。
- **已排期段只按 ddl 时间排序。** ❌ 不做重要性字段、不做优先级打分——主观重要性被"水课偏差"污染：越水的课越容易漏，主观排序会系统性地把最容易漏的事排到最后。
- **列表就是事项本身**（单一节点，无父子、无容器）。同一件事只能出现在一行。
- ~~存疑段置顶提醒~~（D-89 退场）：拿不准的信息一律进**存疑信息库**（§4.12）独立审核页（活动栏入口 + needsHuman 倒序 + 移动确认移除，D-89），不占看板。
- **状态流转 = 改一个状态字段**，不是在容器之间搬运数据。
- **事项详情 = 看板行内展开**（手风琴、单开互斥）：展开体最大 ≈70% 视口、**内部滚动**、滚到顶/底**自然带动页面**（用户 2026-09-27 修订：不锁 overscroll）；框内不放重复标题/收起钮（行标题常驻即收起入口，用户 2026-09-27 修订）；分级默认——基本信息（含摘要，与元素区不重复）、元素级引文收起、编辑列表收起只显计数（D-80）。
- **按标签筛选 / 文本过滤**为客户端行为（D-80 随 UI 重搓交付；用户 2026-09-27 改版：搜索框 `#` 唤起标签下拉、Enter 成 token，选中 token 挂框侧、未选中标签不铺开，多 token AND 收窄）。
- **行快捷按钮（D-83）**：悬停显形——todo 行 = 勾（标完成）+ 归档；done 行 = 归档 + 恢复待办；archived 行 = 恢复待办。
- **对话 @ 提及（D-83）**：输入框 `@` 唤起事项下拉，提及随请求上传、服务端注入给前台做指代消解（「就是那条」不用猜）。

### 4.4 证据链：平等的来源构成链

**一条结论/事项的依据 = 若干条「证据来源」，无主无副，构成一条链**（D-54）。有些消息不止一条主信息，一个结论也常常需要多源互相印证——所以不设主副，只有来源。

每条**证据来源**的组成：

| 组成 | 说明 |
|------|------|
| **内容快照** | 当时看到的那段原文。粘贴的原文天然就是快照；网页/群消息在**接收时抓取**。存本地，永不失效 |
| **来源指针** | URL / 文件路径 / 消息 ID。有就填；它不独立作为证据存在 |
| **时间戳** | 什么时候抓到的 |
| **由谁** | 必备：判断由谁做出，**含模型标识与版本**（推断记录 §4.8 也是链上一环，其「由谁」即 agent0） |
| **支撑对象** | 这条证据为谁作证——**自由标签**（Q19a）：固定元素标签（name/dueDate/summary）与自由元素标签（`元素:<标签>`）**同层、不分类**。证据挂信息元素级，不挂事项级一锅粥（D-62） |

- ❌ **禁止结论只挂在「仅剩链接」的来源上**：只存 URL = 看起来还在、点开是空——最坏的一种静默失效。网络来源必须随接收抓快照；抓不到 → 该来源显眼标「仅指针」（降级可观测，§8.3），不得假装有据。
- **链不分主副、不排序**（D-54）：前端把整条链展开、逐条可看原文；agent0 推理时把整条链当上下文参考。
- ⚠️ **S1/S2 是降级形态**（如实记录）：证据为**平面单跳**（结论 → 证据 → 原文片段）。完整的**链式（DAG）**——知识节点可有父子、子知识可为别的知识的推导结论、证据依附知识节点沿叶子引用到根本证据——**随知识库（S3）落地**，且属**知识库内部形态**（对外契约不变，D-52）。详见 Q19 计划。
- **快照按「来源片段」去重**：片段池 + 引用关系，不是每个字段一份副本。
- 「由谁」字段让「哪些文本被发给了哪个模型」的记录免费获得（对应 §8.1 数据外发的留痕）。
- 事项自带语义名（§4.1）已从结构上防住张冠李戴，证据链定位为**兜底机制**：用户怀疑抽取有误时，展开链一眼看到原文依据。
- 理想形态：**定位与取值分离**——LLM 指出原文片段（只定位），值由确定性规则推导；确需推理时按 §4.8 执行。

### 4.5 Replay 写入模型

| 要素 | 规定 |
|------|------|
| 写入模型 | 每添加一份信息 = **追加一个持久化节点**，不就地修改 |
| 可逆性 | **追加式、可审计**；撤回功能暂缓下架（D-79）——期间修正 = 再发一条更正信息（去重合并接住） |
| 专属 UI | 某事项的**编辑列表**：只读版本史（短 id / 动作 / 由谁）+ 引文批次溯源（L13） |
| 查询 | 当前状态用派生视图（理念文档「派生，不落库」），不每次全量重放 |

⚠️ 撤回重启时必须在 UI 上真的可达——数据模型可逆而 UI 无入口 = 不可逆（当前即处于暂缓状态，已如实标注，D-79）。
⭐ Replay 设计上是**自动化可以激进的许可证**（错合并可撤回）；撤回暂缓期间激进度收窄：低置信进存疑信息库不改正文（D-85，原 D-76 挂靠候选形态已推翻）、冲突自主决断记处理记录不静默覆盖旧值（§4.7），错合并靠用户再发一条更正信息修正。

### 4.6 处理 replay 列表（每个事项一份）

| 层 | 内容 |
|----|------|
| 基础 | 收到过哪些原始输入（每条可展开到原文快照） |
| 处理 | 各固定元素怎么处理的（name/dueDate/summary）、依据什么、由谁（含模型标识）——落地：create_item 的 replay 载荷按固定元素**结构化**承载，详情页「基本信息」照此渲染（D-61） |
| 变更 | 每次持久化 / 修正，按时间排列（撤回暂缓，D-79） |

⚠️ 它**不是调试日志**，是给用户看的处理记录——措辞面向用户，禁止内部堆栈。

### 4.7 矛盾的处理：自主决断 + 显眼标记

两个来源冲突时（含同一条消息内自相矛盾）：

> **不静默挑一个，也不阻塞等裁决：有依据地选 + 显眼地标出来。**

- agent0（裁决者）自主决断，多数情况**优先采信更官方的一方**——官方性判断依据 = 来源身份（`sourceIdentity` 弹性字典，信源适配器填写，整体 JSON 随批次进提示词，D-84）；决断依据（谁发的、何时、从哪、权威性如何）用 `record_note` 记入事项处理记录（详情可查）。
- 矛盾**在事项内标清楚**。⚠️ 标记必须显眼——藏在角落等于静默。视觉标记（⚠️ 状态条）随下阶段前端批次交付，期间处理记录即标记（全留痕）。
- 拿不准的矛盾（判不了谁对）→ 原话入**存疑信息库**（§4.12，D-85），不生成事项、不标存疑。
- 冲突检测属于「真实性」关：一条自相矛盾的信息，真实性本身可疑。

### 4.8 推理的边界：不许无据猜，允许有据推

| | 规则 |
|---|------|
| ✅ 允许 | **有依据的推断**——依据可以是上下文、知识库、来源身份 |
| ❌ 禁止 | **无依据的猜测**——尤其用接收时间兜底相对日期 |
| ⚠️ 必须 | 推断值与原文片段**分开存**（两个字段，绝不互相替换），推断依据链可核查，推断者（含模型标识）可查 |

- 区分标准不是"值是不是生成的"，而是"**能不能被核查**"。
- **截止时刻的推断优先级**（D-66）：① **事情的目的/制度惯例倒推**（如"离校登记应在离校前完成"）；② 同一事项的直接时刻线索；③ 无任何线索才按当日 23:59。⚠️ **禁止借用其他事项的时刻锚点**——把 B 事项的时刻安到 A 上，是张冠李戴的时间版，比留空更危险。
- **时间一律用本地墙钟时间**（D-64）：`YYYY-MM-DDTHH:mm:ss`，**不带 Z / 时区偏移**。本地单机、中国无夏令时——这格式排序=字典序、解析无歧义、库里肉眼可读。LLM 常默认输出 `...Z`（UTC）导致全库偏 8 小时，行动围栏**硬拒收带时区标记的时间**。
- 例：原文「老师说下周要交作业」→ 推断值 2026-10-01（下周上课前），依据 = ①来源身份（英语课官方群聊）②知识库（该课每周三上课）③事件时间。用户随时能展开看到"原文只说了『下周』，日期是 agent 推的"。
- 推断值在 **UI 上必须与原文值可区分**——错但合理的推断比空白更危险（空白让人去查，错值让人直接信）。
- 日期推断的风险与假设（年份补齐、代表时刻）**只能写进 dueDate 元素的 note**（推断徽章/推断说明行的数据源），不得用作存疑理由（D-59）——「我对这个日期做了假设」是依据说明，不是事项疑问。
- 推断失败 → **缺的是信息，不是事件**（D-49）：字段留空位；缺的是日期本身 → 事件进「日期未知」段。**存疑只收「事件存疑」（事项存在性/身份/归属打平），不收「缺信息」。**
- ⚠️ **S1/S2 的推断会降级**（如实记录）：推断依据②（知识库）在知识库落地（§6.5）前不存在——依据只剩来源身份、事件时间、批次内上下文。"该课每周三上课"这类课表知识暂时无法作为依据，推不出 → 日期未知段（字段留空）。勿假装推断很聪明。
- 与「真实性不打分」不矛盾，统一判据：**不可核查的生成值（自评分数）禁止；可核查的推理结论（带依据链）允许。**

### 4.9 知识库（独立模块；S3 落地，对接面已定）

> 知识库在**正式测试使用之后**落地（D-74 顺延；留空期间的推断降级如实记录，见 §4.8；对接面见本节，排期见 §6.5 / §七）。
> 对接面已定（D-52）：**复杂度封装在模块内部，对外只露两个口**。

```
                ┌────────── 知识库（黑盒）──────────┐
 agent0 推理 ──写──▶ 记知识(说法 + 依据指针)          │  内部：贴键？聚类？全文索引？
 （变更清单，走围栏）│                                │  怎么组织是它自己的事，
                │                                │  换实现不动系统里任何别的模块
 agent0 / 前台 ◀─读── 统一返回：原子一句话+依据+状态   │
                │   读法① search_kb   ← 知识库时唯一先建 │
                │   读法② …           ← 想加就加（L9）│
                └──────────────────────────────────┘
  重检 = 第二条读路径：更新 → 代码强制触发 → agent0 推理 → 围栏落笔（可撤回）
```

| 口 | 规定 |
|----|------|
| **写（唯一）** | agent0 变更清单的「记知识」动作，只交**说法 + 依据指针**，走行为围栏（§4.10）。**agent0 不负责整理**——贴键/归类/索引全是模块内部的事。口述给前台、管线抽取两条入口最终都汇到这一个动作，没有第二条写入路径 |
| **读（契约）** | 任何读法返回同一形状：**一句原子的话 + 依据指针 + 状态**。调用方感知不到内部结构。谁挑读法由 agent0 推理决定（自由推理哲学在读这边同样成立） |
| **读法族** | S3 只建读法① `search_kb(query)`（纪律 #4：不预建没有调用者的读法）；新读法 = 模块内函数 + agent0 工具表一行。头脑风暴式读等记延后区（L9） |
| **全量重检** | 第二条读路径（知识库主动找上门）：更新 → 代码强制触发（跳不过）→ agent0 推理哪些待办受影响 → 变更清单走围栏落笔，可撤回（D-29） |

- **内部形态**（主题键 / 全文索引 / 卡片…）= 模块内部实现细节，S3 实测再定；换实现只动知识库自己。判据：「改这个决定要动几个文件？」答：1 个。
- **恢复实施时的既定约束**（D-18/D-28/D-29 延续）：

1. 与事项**完全独立**：存得独立，用得聚合（呈现按 §4.1 组装到事项上下文层）。
2. **每块知识都可作为证据链的一个环节**（§4.8 推断依据②）。
3. **绝不与事项字段重复存同一事实**。判据：「这句话脱离具体事项还成立吗？」成立→知识库（"英语课每周三上课"）；不成立→事项字段（"作业 10-08 交"）。
4. 条目（返回单元）= **原子一句话 + 依据 + 状态**；第一版只做**明示事实**（有人明确说过、可引原文快照）；归纳模式、来源特征不做（D-28）。
5. 必须参与判决（推断依据 / 上下文组装 / 问答），不是只写不读。
6. ⭐ **每次知识库更新或信息增加，强制重检每一个待办**（不是"重算受影响的"——判断哪些受影响本身就要全量比对，且筛漏=静默失效）。变更**自动应用**（Replay 可逆）+ 必须在事项的 replay 列表里**显眼可见**。实施时记录重检耗时与改动数，先测量再优化。
7. 知识修订不重算历史结论：标「依据已变更」，由用户决定。

### 4.10 处理架构：自由推理 + 行为围栏（agent0 的作业方式）

**处理不是流水线，是 agent0 的作业方式**（D-50 提出框架，D-51 定稿）：

```
① 入口：待处理队列的 RawInput（原文已落档，永不丢失）
② 自由推理：agent0 一次对话式推理，自行决定查什么、查几次、想多深
   可用工具全是真代码检索（search_items / search_kb / get_item）——LLM 永不裸操作存储
   推理时自我照顾固定元素（见下表）
③ 产出：变更清单（系统里唯一的 schema）；【空清单完全合法】
   [{动作：合并|新建事项|填字段|记矛盾决断|入库（park_uncertain，D-85）|记知识|…,
     目标/新实体, 值?, 证据指针[→片段池ID]}]
④ 行为围栏（代码，只查行为，不查观点）：
   硬拒收 = 引用的 ID 不存在 / 动作不在白名单 / 非独占写路径 / 格式不完整 / 引文非原文逐字（空白归一后比对）
   拒收项报错回给 agent0，可修正清单再提交一次；再失败放弃该项并留痕
   ⚠️ 围栏不评判提取对错（日期对不对、合并准不准、值不值得记）
⑤ 逐项落笔：合格项各自成为 Replay 节点（可撤回、留痕、由谁含模型标识）
⑥ 事后兜底：证据链可查 → replay 列表显眼可见 → Replay 可撤回
```

⭐ **零变更是合法产出**：消息可能没用、只有一点点、不全面、不权威——agent0 有权判定不值得动任何待办或知识库，留痕（"评估后未采用"）了事，原文永远在 RawInput 档案里。这同时是防噪声的闸门（成功判据 #3：不制造新噪声）。
⭐ **围栏只校验行为正确性，不校验信息提取正确性**：引用是否存在、动作是否合法，代码说了算；日期抽得对不对、合并判得准不准，围栏无权否决——那没有机械判据，硬造就是死板。理解质量由事后三层兜底：证据链可查、replay 列表可见、Replay 可撤回。

**固定元素**（推理时自我照顾；事后在 replay 列表逐项可核查）：

| 固定元素 | 内容 | 判不了 / 不采用时 |
|--------|------|--------------------|
| 身份判定 | 是不是已存在的同一件事？（候选集 = 已有事项 + 存疑存量，命中即提升） | 多候选打平 / 低置信拿不准 → **存疑信息库**（§4.12，D-85；候选注记写进条目理由），不再生成存疑事项 |
| 标签 | 打什么标签？ | 多候选打平 → **存疑** |
| 真实性 ⭐ | 依据能不能被查？ | **证据链，不打分** |
| ddl | 是哪个字段的日期？（防案例 2） | 字段留空 + 事项进**日期未知段**（§4.2），**绝不猜** |

- **真实性 = 可核查的证据链，不是分数。** 分数本身就是生成值，违反「只定位，不生成值」。一条「听说英语要加口语考试」的证据链显示「来源：用户口述，用词『听说』『不确定』」——比任何 0.3 都准确，且是可核查的事实。
- **身份判定保留置信度分级**（确定性 / 中高 / 低）——它是 agent0 要做的决定，需要依据决定自动合并与否；用户要求「信度标出」。与真实性（属性，给人查）机制不同，**不得统一成一个 score 字段**。

### 4.11 多源碎片的去重与合并（S2）

同一件事会有至少两次输入（课上碎片 + 群里正式说明）。识别不出 = 看板上两条重复事项。

| 要求 | 说明 |
|------|------|
| 关联判断 | AI 结构化时判断新碎片是否属于已有事项，按 §4.10 身份判定执行，置信度分层（见下） |
| 合并保留全部原始快照 | 合并后的事项能看到"由哪几条碎片合成"，每条可展开原文 |
| 不确定时不许静默 | 判不了 → 存疑。既不静默合并（可能合错），也不静默分开（产生重复） |
| 裁决权唯一 | 需要全局视野的判断只有一处做出 |

**置信度分层**（§4.10 身份判定的输出）：

| 置信度 | 处理 |
|--------|------|
| 确定性证据（共享原文片段 / 可定位的同一实体串） | 自动合并 |
| 中高置信 | 自动合并——**不标信度**（D-75：依据由证据链自身承载，标签是重复记账） |
| 低置信（无论有无候选） | **存疑信息库**（D-85 修正 D-76：原「挂靠候选事项」已推翻——模糊信息不挂事项）：原话逐字入库 + 需人工分与理由；后续信息到来 AI 检索合并升格 |
| 多候选打平、无依据取舍 | **存疑信息库**（原「存疑附候选注记」随 mark_doubt 退役，D-85） |
| 低置信但"可能相关"→ todo | ⏸️ **明确延后**（L1），不许顺手实现 |

### 4.12 存疑（存量兼容）与存疑信息库（不确定信息的唯一去处，D-85）

**~~事项存疑段~~（D-89 退场）**：`doubtNote` 字段与 mark_doubt 时代的存量事项的 UI 展示已全部退场（存量已解除）；agent0 判据自 D-85 起为「拿不准 → 存疑信息库」，词表无 mark_doubt（resolve_doubt 保留作数据层消化出口，无 UI）。

**存疑信息库**（`uncertain_inputs` 表，信息层池子）：拿不准的原始信息直接进库，**不生成事项、不挂候选**——模糊信息不强挂事项（用户 2026-09-28：「这没必要强把模糊的信息挂在事项上」）。统收三类：①修改类说法目标不明（原「未确认变更」概念作废）②低置信碎片 ③矛盾悬而未决。

- **条目 = 原话逐字 + 信源快照（弹性字典）+ 事件/接收时刻 + 来源批次引用 + needsHuman（0-100，agent0 打的「需人工分」）+ 一句理由**（缺什么信息、官方性、能否定量的语义都在理由里）+ 状态。
- **生命周期**：`open → merged | discarded`。**agent0 可合并可丢弃**（均记 note 留痕可查），人工同权（翻池界面随后端端点之后的前端批次）；**不去重**（同句重复出现各建条目，AI 检索时自行判重）；**无机械保质期**——时刻随条目暴露给 AI、排序带时间衰减、同源对账时 agent0 发现被取代就丢弃留痕：状态变更全由判断触发，无一由时钟触发。
- **复原双通道**：
  1. **AI 自动**——agent0 消化新批次时自主检索库（`search_uncertain`，信源接近度排序：同群 > 同发信人 > 时间临近 > 新入库，隐式携带当前批次参照），命中即大概率是「当初切开的上下半句」→ 合并应用，条目转 merged。何时查/查哪个由 agent0 判断，不写死流程。
  2. **人工**——「需人工分」排序的查询端点（`GET /api/uncertain`，最需要处理的浮前）+ 清扫循环（对话触发或 `POST /api/uncertain/sweep`：逐条复评，被取代/证伪/重复 → 丢弃留痕，仍有效 → 可降分）。
- **AI 的检索面 = 存疑库 + 已整理事项（search_items/get_item）+ 历史批次（search_recent_raws）**，全部由 agent0 自主决定调用时机与合并方式。
- 缺日期、缺字段仍不进这里（那是日期未知段 / 空位，D-49 判据不变）；「拿不准」≠ 缺信息。

> 历史注：「裁决队列」已退役（D-40）——归属打平先并入库疑（D-40）、D-85 起改入存疑信息库；指令歧义按 §4.14 处理，不再设独立分类。

### 4.13 搁置与归档

> ⏸️ **延后（L-17，用户 2026-09-28：「我暂时不需要搁置」——移出信源阶段）**：归档的**最小形态已随 D-83 上线**（用户对事项直接归档、走版本链）；搁置（shelve）与搁置→归档流整块延后，以下设计原样保留备查，实现不许顺手做。

**搁置**（隐身名单，唯一由用户放入）：

> **语义铁律：搁置是「不活跃但保留且可复活」，绝不是「待删除」。禁止实现任何"清空"功能。**（原名"回收区"已弃用。）

- 形态 = **一个安静的事项类别**：静静躺着，不挂到别的事项上下文里、不参与 ddl 排序、不占看板。**对用户只写**：放进去就放下，由 agent0 读它。放进去的代价**非常低**（一次点击），结果**可见且可撤回**。放弃 = 追加一个状态节点，不是删除。
- **agent0 照常访问搁置区**：消化新信息时正常匹配。**切确的、需要处理的信息命中 → 主动提起**：事项恢复活跃、按其日期回到看板对应段，replay 列表记录"由搁置提起"（D-46）。
- 用户自主确认了结 → **归档**。
- 它是看板膨胀的泄压阀：没有它，唯一能"移除"的办法是标完成（撒谎）或删除（不可逆）。

**归档**（终态）：

- 提起并处理完毕、或用户确认"这事了结了"的搁置事项进入归档；活跃事项也可由用户直接归档（D-83）。**不删除**（Replay 精神），但**离开活跃上下文**。
- ⭐ 动机是**上下文经济**：agent0 的日常工作上下文 = 看板活跃段（存疑 / 日期未知 / 已排期）+ 待处理队列；搁置 = 摘要 + 可检索；归档 = 不进上下文，仅显式检索。不归档，了结的事会永久占用 agent0 上下文。
- 归档列表不按 ddl 排（它不是待办），按归档时间倒序。

> ⭐ 「按 ddl 排」**只约束看板的已排期段**。搁置、归档都不是待办，不参与 ddl 排序，各有简单的次级规则。

### 4.14 前台客服 AI：对话 buddy（查询器/助手层）

**前台客服是一个有连续上下文的多轮对话子 agent（buddy）**：像聊天一样答问、收信息、执行用户指令，按需调用工具——而不是把每条消息死板三分类（D-78：单条意图三分法退役为内部产出，不再是对外交互形态；这是对 D-38「对话子 agent」本义的回归）。它独立于处理环节、只读、绝不直接写库；写权只属于执行器，前台只能**调用工具**触发。

| 用户在做什么 | 前台做什么 | 落库 |
|------|------|------|
| 咨询（"最近有什么要交的"） | 调只读查询工具 → 对话式回答 | ❌ 不产生任何事项节点 |
| 提供新信息（粘贴通知、随口说事） | 调 `ingest(text)` → RawInput 进待处理队列 → agent0 完整处理 | ✅ 走全程审核与裁决 |
| 要求撤回历史 | 如实告知暂不支持（D-79），引导直接发更正信息（走合并） | ❌ |

- **会话上下文**：前台维护连续对话，多轮指代（"就是刚才那条"）靠上下文解析。会话只是对话记录，不构成任何写权。
- **单输入框纯对话不变**（D-58 原则延续）：❌ 不设「选择输入类型」的 UI 旋钮——判断什么是资料、哪句话是指令，都是前台的工作。
- **改数据**：修改类说法按新信息走管线（去重接住）；目标唯一命中 → update_item 应用（追加修正版本）。目标不明 → **不猜、不应用、不当面追问**，原话入**存疑信息库**（§4.12，D-85——「未确认变更」概念已废），后续信息到来由 agent0 检索合并。**底线不变：绝不猜着应用。**
- **意图拿不准时：宁可误录入，不可误丢失**（误录入 Replay 可撤回，误丢失不可逆）。完全无信息量（纯寒暄）→ 丢弃留痕，不进库制造噪声。

**前台客服可调用的工具**：

| 工具 | 用途 | 阶段 |
|------|------|------|
| `ingest(text)` | 把新信息加入**待处理队列**（处理入口） | S1 起 |
| 只读查询（看板/事项/存疑库） | 咨询回答，不经过任何写路径；含 `search_uncertain` 对话翻池（信源阶段起） | S1 起 |
| @ 提及（输入框 `@` 选事项） | mentions 随请求上传，注入给前台做指代消解（D-83）；id 由前端看板保证真实 | UI 阶段起 |
| 触发存疑库清扫 | 前台只触发不写库——服务端清扫循环逐条复评（§4.12，D-85） | 信源阶段 |

**agent0 作业时可用的检索工具**（§4.10；写入不经工具——经行为围栏校验后由独占执行器落笔）：

| 工具 | 用途 |
|------|------|
| `search_items(query)` | 在事项中检索候选（身份判定 / 打标签） |
| `search_kb(query)` | 知识库读法①（§4.9 契约）：推断依据 / 上下文组装 / 问答。知识库落地（§6.5）起可用，之前返回空 |
| `get_item(id)` | 读单个事项（元素 + 证据 + 片段 + 版本史） |
| `search_uncertain(...)` | 检索**存疑信息库** open 条目（信源接近度排序，隐式携带当前批次参照）——复原通道 + 对话翻池共用。信源阶段（D-85） |
| `search_recent_raws(...)` | 按时间相近+同来源检索历史批次——散落碎片的兄弟找齐（QQ 多块通知兜底）。信源阶段（D-76/D-85） |

**继承禁令**：❌「你还有 N 件事没看」式措辞；❌「建议你关注…」式主动推荐；受「『我不知道』是功能」约束——无依据时明说没有，不得用常识补全；部分依据时有据与无据分开陈述。

### 4.15 事项状态与过期

| 状态 | 表现 |
|------|------|
| 待办 | 正常展示，按 ddl 排序 |
| 已完成 | 用户主动标记；系统不代替用户执行写操作 |
| 已归档 | 用户主动归档（D-83 最小归档提前）；进看板归档段（按归档时刻倒序）；「撤回归档」只撤归档——归档前若已完成则回到已完成（D-83 二轮）；搁置流 ⏸️ 延后（L-17） |
| **已过期** | ⚠️ **必须如实、显眼地展示，绝不隐藏或静默移除** |

- 过期 = **渲染时派生**（ddl < 当前时间），不是存储字段——延续「派生，不落库」（§4.5）。
- 已完成可由用户**恢复为待办**（D-82）：详情按钮直发、与标完成对称、走版本链留痕——误标可逆。
- 已完成段**按完成时刻倒序**展示（用户 2026-09-27）；完成淡出梯度同样锚定完成时刻。

系统不能防止所有遗漏，但**必须让遗漏可见**——这是"敢不看"的信任基础。

## 五、输入设计

### 5.1 capture-first, triage-later

记录的代价必须低于「判断要不要记录」的代价。任何要求用户先判断"重不重要"的输入设计都会复现案例 1——那个判断恰恰是当下失灵的东西。先无脑捕获，事后 AI 分诊。

### 5.2 两段式方案

| 环节 | 载体 | 做法 |
|------|------|------|
| 捕获（30 秒内） | 手机自带备忘录 / 微信文件传输助手 | 随手打几个字。不结构化、不分类、不判断重要性 |
| 处理（回到电脑） | 电脑端系统 | **批量粘贴**导入，AI 负责结构化、拆事项、排序 |

- ❌ 不做手机 App、不做多端同步。
- ✅ 「粘贴一大坨混乱文本，系统自己拆」是 MVP 核心能力，不是附属功能。
- 备忘录自带时间戳 = 天然的事件时间，粘贴时可一并带入。

### 5.3 RawInput 边界

```
RawInput {
  内容        // 原始文本/文件内容
  来源类型    // chat / paste / nc / ...
  来源身份    // 弹性字典（D-84）：core 契约只约束是对象 + 保留键 sourceLabel（D-88 由 name 改名）
              //（如 {"sourceLabel":"英语课官方群","groupId":"123","sender":"学习委员"}）
              // 适配器填什么存什么，整体 JSON 进 agent0 提示词（推理依据 + 外发粒度 + §4.7 官方性判断依据）
  接收时间    // 什么时候进来的
  事件时间    // 事情发生的时间。可选，可为空；nc 等自带时刻的信源用它（比到达时刻真实，两者差距本身是信息）
  ── DB 归档列（不进 shared 类型，仅 DB 存档）──
  raw         // 信源原始载荷 JSON 留底（D-84；nc 事件原文；chat/paste 的内容即原文，可空）
}
```

- **所有输入（含用户对话）统一走这条边界**，它是将来加任何新源的唯一改动面。⚠️ 这**不是**插件系统：不定义插件 API、不做加载机制、不做沙箱。
- RawInput 带**消化状态**（未消化 / 已消化）：进料口可见，不是看板行；agent0 消化完毕置「已消化」（AI 失败的「未处理」降级标记另计，见下）。
- 相对日期规则：

| 情况 | 处理 |
|------|------|
| 事件时间已知 | 以它为锚解析「下周」等相对日期 |
| 事件时间未知 + 文本含相对日期 | ❌ 禁止用接收时间兜底（无据的猜）。可有据地推（§4.8），推不出 → 日期未知段（字段留空位） |
| 绝对日期（"10月8日"） | 直接解析；年份缺失按下方顺序找据（D-72）；推不出 → 日期未知段（字段留空位） |

- **缺年份的推断顺序（D-72）**——命中即停：① 文本自带的年份线索（"2026级""2026年中秋节"）；② 通知自称的时间锚（"9月24日（今日）"= 通知书写日，年份跟它走）；③ 事件时间同年；④ 月-日今年未到 → 今年；⑤ 月-日今年已过 → **默认当年、如实过期**，只有文本有明确「面向未来」依据（"明年""下学期""下届"，或年度节点且语境为预告）才取下一年；⑥ 回溯性日期（"登记日期写2026.8.30"这类往表里填的日期）不是 ddl，不建 dueDate 元素。理由（不对称性）：错成「已过期」是**显眼的真话**（扫一眼知道是旧闻），错成「下一年」是**隐形的假话**（事项假装还有一年寿命，且大概率永不发生）——积压批量粘贴的旧通知是常态场景。

- ⚠️ **粘贴 ≠ 指令**（D-48）：粘贴批次里的一切内容都是**信息**，永远不触发修改/指令逻辑；**指令只能来自对话中用户本人的发言**。群通知里的"作业改到周五交"是资料，不是你的修改意图——即使它长得像指令。
- **批次粒度**：一次粘贴 = **一个** RawInput（哪怕里面混着三件不相关的事）；agent0 在批次内部拆事项，片段池存碎片，证据链引用指向批次。
- 用户对话是一个「源」，但前台客服不是"采集器"：它调 `ingest` 把文本放入待处理队列，写权仍在 agent0。对话产生的原始输入**就是证据链的终端引用节点**——若发现原始输入没被任何结论引用，说明证据链断了。
- **AI 不可用的降级**：原始文本**先原样落盘，然后才交给 AI**。AI 失败时原始记录仍在，看板标「未处理」，绝不静默丢弃。顺序错了就会把"AI 挂了"变成"数据没了"。
- **重试口（D-71）**：「未处理」批次可重试（看板横幅按钮 → `POST /api/raw/:id/retry`）：状态回「未消化」、重走完整消化管线。**仅限「未处理」批次**——已消化批次重试会把同一批变更重复落库（变更非幂等）；而失败批次执行器整批回滚过，库内无半套状态，从头重跑安全。

## 八、约束

### 8.1 产品约束

| 约束 | 规定 |
|------|------|
| 不托管凭证 | 需要交出账号密码才能采集的源不做（QQ 是否破例 = L4，信源阶段之后） |
| 只读 | 绝不代替用户对外部系统执行写操作。⚠️ 用户修改**自己的库**不在此列（`correct` 是代用户执行用户自己发起的修改） |
| 锚点可选 | 增强配置一律可选；缺失时降级，而非拒绝工作 |
| 数据外发 | 前期一律在线 LLM。已作为**知情选择**记录：文本可能含他人学号/名单/联系方式；「由谁」字段自动留下外发记录（L5 控制手段延后） |
| 推送与红点 | 见 §8.2 两处修改 |

### 8.2 对《核心理念》的两处有意修改（冲突时以本节为准）

1. **「不推送」→「有限推送」**：日常层 = 环境化提示（不弹窗不打断，瞟一眼即可）；打断层 = **只有「不可逆 + 临近」才主动推送**。阈值必须保守，宁可少推（误报摧毁信任）。
2. **「禁止红点/未读数」→「允许数字统计」**：但保留禁令——**禁止「你还有 N 件事没看」式制造愧疚感的措辞**。数字统计 ≠ 愧疚式提醒。

### 8.3 架构与工程约束

- **把变数拿到模块内部**：对外稳定接口，内部随意改。
- **去耦合**：加新源成本要小（信源阶段实测 ≤ 30min）。
- **一份数据只有一个所有者**：跨模块访问必须经过所有者。
- **数据模式按场景选**：CRUD / Replay / 树形 / 图状都是工具，不因优雅而采用。
- **不按流程切模块**：按「什么时候会变」分。判据：「改这个决定要动几个文件？」答"好几个" ⇒ 它们本来是一件事。
- **降级必须可观测**：可以失败，不许静默——留痕且让人看得见。
- **「无数据」不得显示为「通过」**：假绿灯比没有检查更危险。
- **看到异常先怀疑自己**：把一次 bug 当"客观规律"会锁死一条本可行的路。
- **每句注释都要能回答「你怎么知道？」**：答不上来就删，或明确标为**意图**。不许"听起来像事实的猜测"存在。
- **多借鉴别的项目**，不自己一味猛做。

### 8.4 TS 全栈硬约束

- **类型必须真正共享**：单一 `shared/types` 包或 monorepo workspace，前后端同源引用。**验证方法：改掉一个字段名，前后端应同时编译失败**；只有一边失败 = 类型没共享 = 付了 B 的成本拿到 C 的缺点。
- **strict 模式，禁止 `any`**（类型是护栏）。
- 不引入非必要抽象层（不必要的 ORM、状态管理库、微服务化）。
- 测试在**真实入口**断言**用户看到的那行字**。
- **选型已定（N1，D-55；UI 部分经 D-81 修订）**：npm workspaces 单仓（`apps/server` / `apps/web` / `packages/shared` 共享类型；不上构建工具链）；前端 **React + Vite**（内置 hooks 状态，不引 Redux/Zustand/状态库；UI 样式 = **Tailwind v4 + shadcn/ui 风格**——组件源码进仓库非黑盒依赖，修订 D-55 的「不引组件库/Tailwind」）；后端 **Fastify**（内置参数校验，与行为围栏契合）；存储 **Drizzle ORM + better-sqlite3**（单文件拷贝即备份；表结构即 TS，形状错误编译期报错——D-33 护栏在数据源头的延伸）；LLM **openai 官方 SDK 走 OpenAI 兼容协议**（baseURL 指向具体服务商：DeepSeek/GLM/OpenAI/未来本地 Ollama 皆可，换模型只改配置；API key 存本地配置文件，不进仓库）；测试 **Vitest**（集成测试 fetch 打真实 HTTP 入口；Playwright 不预建）。
- **质量工具链（D-56）**：tsconfig 六开关（noUncheckedIndexedAccess、noUnusedLocals/Parameters、noFallthroughCasesInSwitch、forceConsistentCasingInFileNames、verbatimModuleSyntax）；ESLint 重点 no-floating-promises（忘 await = 静默失败）+ no-explicit-any；Prettier + eol=lf + pre-commit/pre-push 钩子；knip 死代码巡逻（`npm run check:dead`，不挡提交）；**zod 做运行时边界校验**（ingest 请求体 + LLM 变更清单；schema 在 packages/shared，一份三处用）。
