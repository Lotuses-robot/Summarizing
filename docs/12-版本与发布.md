# 12 · 版本与发布规范

> 性质：**长期有效的操作规范**（与 07/08/09/11 同级）。批次 2「代码侧上云项」产物之一（docs/11 阶段 2）。
> 目标：让「什么算一个版本、怎么切、怎么发」有单一出处——部署只跟 tag，CHANGELOG 与 GitHub Release 同源。

## 一、版本号（0.x 阶段）

采用语义化版本 `v主.次.修`：

- **主版本**：0 — 「1.0」留给「核心业务闭环稳定 + 对外正式发布」。在此之前一直是 0.x。
- **次版本**（`0.X.0`）：一次**阶段批次**的推进（如 006 多用户、批次 2 上云）。
- **修订版**（`0.x.Y`）：同批次内的修复/小改。

⚠️ **部署只跟 tag，不跟 main HEAD**（docs/11 阶段 2 红线）：服务器上跑的是某个 `vX.Y.Z`，不是一个会漂的 HEAD。
本地全绿 ≠ 可发布；发布 = 打 tag 触发 CI 出制品。

## 二、CHANGELOG.md

### 2.1 格式硬规范（不遵守会导致解析或阅读出错）

- 中文、按版本倒序累计（新版本在最上，旧版本在下）。**与 GitHub Release 说明同源**——Release 的正文即该版本 CHANGELOG 段落。
- 版本标题固定写：`## [vX.Y.Z] - YYYY-MM-DD`（日期用北京时间、当天发布日；未发布的草稿放 `## [未发布]`，切版本时改成正式标题）。
- ⚠️ **版本段内的小节一律用 `###`，不得用 `##`**——解析器（关于弹层 / 发版说明）以 `##` 识别版本边界：段内出现 `##` 级标题会把其后内容静默截断（审查 2026-10-14）。
- 每个版本一段，结构固定为：`### 一句话主题` → 若干 `- ` 条目。**不用三级以下标题、不用表格、不用嵌套列表**（解析器与 GitHub Release 都只认这种平铺结构）。
- 每条目一行的 `- ` 列表项；同层条目不得再缩进建子列表——要补充说明就写进同一行（用「→」「；」「（）」衔接）。
- 代码/字段/命令用反引号 `` ` ``；面向用户的界面文案用「」括起，不使用 markdown 链接以外的行内 HTML。

### 2.2 措辞规范（读者是用户，不是开发者）

- **说人话**：只描述「用户能看到/能感受到的变化」，不写内部术语与实现细节（不出现函数名、类型名、框架名、设计模式名）。
- **不用生僻开发词汇**：如「幂等」「原子性」「下沉」「收敛」「回退链路」「TOCTOU」「SSRF」等——改写成用户视角的描述（例：不写「修复 SSRF 白名单 TOCTOU」，写「图片下载只允许公网直链，下载时锁定已校验的地址，防止被重定向到内网」）。
- **每条讲清「改了什么 + 为什么 / 影响」**：先说发生了什么变化、再说对用户意味着什么（旧行为 → 新行为），一句话能读懂，不必读第二遍。
- **不吹不藏**：如实写，不夸大（不写「大幅提升」「彻底解决」）；修复类条目说清原来是哪里不对。
- 面向用户的产品名、功能名与界面保持一致（如「信源」「存疑库」「事项」）。

### 2.3 分节（可选，按需使用）

- 条目较多时，用 `###` 分为「新特性」「修复」「其他」三节（无内容的小节不写）；条目少时只用一个 `### 一句话主题` 节即可。
- 破坏性变更单独用 `### 破坏性变更` 一节并在首条醒目说明（升级/迁移影响）。

### 2.4 流程

- 开发中的改动先记在 `## [未发布]` 下，切版本时把该段标题改成 `## [vX.Y.Z] - YYYY-MM-DD` 并按上表规范通读一遍措辞。

## 三、发布流程（tag → CI → Release）

1. 确认 main 全绿（`npm run check`）；跑一次便携包本地构建（`npm run build:release`）确认制品可出。
2. 把 `CHANGELOG.md` 的 `[未发布]` 段落改为 `## [vX.Y.Z] - YYYY-MM-DD`。
3. 提交、推 main。
4. 打 tag：`git tag vX.Y.Z && git push origin vX.Y.Z`。
5. CI（`.github/workflows/release.yml`）自动：
   - `check`（质量门）→ `portable`（windows-latest 出 `summarizing-portable-win-x64.zip`）→ `release`（建 GitHub Release、挂便携包附件、说明用 `generate_release_notes`）。
   - 镜像构建默认**关闭**（`image` job）；装好 Docker / 配好 ACR secrets 后，手动触发 workflow 并勾 `build_image`，或启用该 job 的 tag 条件。
6. 校验 Release 页附件齐全、说明可读。

## 四、镜像发布（服务器用）——待 ACR 就绪

- 形态：CI/本地构建 → 推国内 registry（如阿里云 ACR）→ 服务器 `pull`（**不在 2C2G 服务器上 build**，避免内存尖峰，docs/11 阶段 2）。
- 需要的仓库 secrets（`.github/workflows/release.yml` 的 `image` job 引用）：
  - `ACR_REGISTRY`（如 `registry.cn-shenzhen.aliyuncs.com`）
  - `ACR_NAMESPACE`
  - `ACR_USERNAME` / `ACR_PASSWORD`
- 镜像 tag 用发布 tag（`vX.Y.Z`）；服务器 compose 里把 `image:` 指向它（见 `docker-compose.yml` 注释）。

## 五、回滚

- **「仅向前」**：不写 down 迁移。回滚 = **恢复迁移前备份 + 回退镜像 tag**（docs/11 阶段 2；备份机制见 `apps/server/src/storage/migrate.ts`）。
- 升级/回滚的完整操作步骤见 `docs/13-部署运维.md`（升级 runbook）。
