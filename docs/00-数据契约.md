# 00 · 数据契约（重构权威）

> **本文件是「重构后数据模型」的唯一权威**。01-规格 是整体规格，本文件是数据层的精确契约。
> 状态：**已定稿、现行有效**（D-70 定稿；原「草稿待审定」措辞已于 2026-09-29 更正——S1 起代码即据此实现）。
> 立约背景（2026-09-25）：用户审查中发现「任务/事件」两层模型的代价（单事项也要造容器、呈现与模型错位、归属成为 LLM 必做决策），逐轮收敛为「事项 + 标签 + 知识」的单一节点模型。

---

## 一、模型总览（一句话）

**系统只有两种节点：左侧「事项」，右侧「知识」；事项靠标签归类，事项指向知识作依据。**

```
              左侧                          右侧
    ┌──────────────────────┐      ┌──────────────────┐
    │  事项 (Item)          │      │ 知识 (Knowledge)  │
    │   · 语义名            │─依据→│  · 原子一句话      │
    │   · 日期（可空）       │      │  · 出处（原文快照）│
    │   · 摘要              │      │  （最低级，不互相引用）│
    │   · 信息元素[]        │      └──────────────────┘
    │   · 标签[]            │
    └──────────────────────┘
             ↑
         可持久化（版本链）
```

**只有两类边**：
1. `事项 → 知识`（依据，单向）
2. `事项 ↔ 标签`（成员关系，多对多）——标签不是节点，是事项上的字符串属性

**没有的**：任务容器、任务树、嵌套、知识↔知识引用、推理链。

---

## 二、名词（重构后的正式术语）

| 术语 | 定义 | 取代了原来的 |
|------|------|-------------|
| **事项（Item）** | 最小可追踪单元：自带语义名 + 可空日期 + 摘要 + 信息元素 + 标签。看板的一行。 | 原「时间锚点事件」 |
| **标签（Tag）** | 事项上的自由字符串，用于归类/筛选。可多个、可没有。 | 原「任务」（降级为标签） |
| **信息元素（Element）** | 事项内部的结构化条目（标签+内容），**不是独立节点**，随事项一起存取。 | 同名（Q15/Q16，D-63） |
| **知识（Knowledge）** | 最低级原子事实（明示事实），带出处。**不互相引用**。 | 同名（知识库落地时） |
| **依据（Basis）** | 事项/信息元素指向的原文快照 或 知识。 | 原「证据链」的边 |

⚠️ **「任务」「事件」「时间锚点」这些词在重构后退场**——旧文档、旧代码、旧验收清单里的它们，一律替换为本表术语。

## 三、事项（Item）——唯一的左侧节点

### 结构

```ts
Item = {
  elements: Element[],            // 内容（全元素化，见 §四）
  tags: string[],                 // 归类标签（独立字段，不是元素，不挂证据）
  status: "todo" | "done" | "archived",  // 处置状态（独立字段，不是元素；archived 于 D-83 启用，shelved 仍预留）
  doubtNote: string | null,       // 存疑标记（独立字段，不是元素；⚠️ D-85 起停新增——agent0 拿不准改入存疑信息库，字段保留兼容存量）
}
```

**元素只装「内容」**（来自原文、可查回原文的东西）。**归类（tags）与状态（status/doubtNote）是独立字段**，不进 `elements[]`（用户 2026-09-25 定）——它们不是"关于这件事的内容"，是"对这件事的归类/处置"，无需原文依据。

### ⚠️ FIXED_LABELS —— 易漏改的脆弱点（重点维护）

```ts
// 固定元素名的集合（唯一来源）。自由元素的 label 必须不在此集合内。
const FIXED_LABELS = ["name", "dueDate", "summary"] as const;
```

**为什么醒目**：这张集合 + `elementSchema` 的判别联合成员 + UI 的固定元素渲染顺序，**三处必须同步**。漏改任一处 → 静默出错（如：新固定元素没进 FIXED_LABELS → 被当成自由元素 → 不校验、不按固定位置渲染）。

**维护规则**（加/删固定元素时**必须全做**）：
1. `FIXED_LABELS` 加/删该名字
2. `elementSchema` 的判别联合加/删对应 extend 出来的元素
3. 校验用 `.refine` 保证「自由元素的 label 不在 FIXED_LABELS 内」（防冒名）
4. （若有）UI 固定元素渲染顺序表同步
5. **收尾自检**（见 §十）：grep 这三处是否一致

**降错手段**：把三处**从同一常量派生**（如 UI 顺序表从 `FIXED_LABELS` 映射生成），把「三处同步」压成「一处定义」——实现时优先这么做。

### 语义名、日期、标签的取值

- **语义名** = 查找 `label === "name"` 的元素 → `text`（非空，禁裸日期——防张冠李戴，原 §4.1 的收益保留）
- **日期** = 查找 `label === "dueDate"` 的元素 → `text`（本地墙钟，null = 日期未知）
- **标签** = `tags[]`（自由字符串，多对多，可空——不强制归类）

### 与原「事件」的差异

| 原来 | 现在 |
|------|------|
| `taskId`（挂在任务下） | **删掉** → 改为 `tags: string[]` |
| 任务树 `parent_id` | **删掉**（无层级） |
| name/dueDate/summary 平铺字段 | **改为固定元素**（§四） |
| `status`/`doubtNote` 平铺字段 | **保留为独立字段**（不是元素） |
| `dueDateBasis` 字段 | **删掉**（并入 `元素:dueDate` 的依据/说明） |

### 持久化（追加式版本链）——事项级

- **持久化单位 = 事项**（含它所有元素、标签、依据）——**元素搭事项的便车**，不单独版本化
- **知识不做版本**（选 b）：改了扫一遍引用它的事项，标「依据已变更」（原 D-29）
- 机制：**追加式版本链**

```
Item 版本链：v1 → v2 → v3   （追加，永不删）
  每个版本 = { itemId, 完整快照(elements+tags+status+doubtNote), at, by, action }
    by = 变更署名（D-88）：{ actor: string, model: string|null }——谁 + 什么模型；
         不含来源（信源身份走证据链：版本→证据→片段→批次→sourceIdentity）
  当前视图 = 每条链最后一个版本
  撤回：设计定稿（追加 revert_version 节点、snapshot 取前一条，只撤最新、create 不可撤），
        功能暂缓下架（D-79）——期间修正 = 再发一条更正信息（去重合并接住）
```

- **不用**：可持久化线段树 / 路径拷贝 / 哈希版本 / 反向边索引（推导链是"算出来的"，不预建推理）；也不做「撤销标记 + 派生跳过」——那要改派生读路径（D-77 评审定）
- **撤回重启时不能静默**：留痕设计已在案（D-77：撤回节点本身进版本史）；知识引用的「依据已变更」随知识库落地（原 D-29）

### 派生（两个纯函数，都是 view 不是 model）

| 函数 | 用途 |
|------|------|
| `deriveCurrent(log)` | 当前有效状态（agent0 / 看板 / 详情）——取每链最后一条 |
| `deriveHistory(log, itemId)` | 该事项的完整变更史（编辑列表 / replay） |

## 四、信息元素（Element）——事项的唯一内容载体

### 命名（用户 2026-09-25 定）

| 名字 | 指什么 |
|------|--------|
| **`label`** | **元素名**（`name` / `dueDate` / `链接` / `地点`…）——标识这是哪种元素 |
| **`tags`** | **事项的归类标签**（数据结构课、作业…）——事项上的独立字段（§三） |

### schema 家族：根本类型 + 衍生类型（两层）

```ts
// ── 根本类型：所有元素的长相（存储层只认它）──
const baseElementSchema = z.object({
  label: z.string(),
  text: z.string(),
  basis: z.array(basisSchema).default([]),   // 依据（指向原文/知识，见 §五）
});

// ── 固定元素：extend —— label 定死 + text 收窄（每个固定元素一行）──
const nameElement    = baseElementSchema.extend({ label: z.literal("name"),    text: z.string().min(1) });
const dueDateElement = baseElementSchema.extend({ label: z.literal("dueDate"), text: localWallClockSchema.nullable() });
const summaryElement = baseElementSchema.extend({ label: z.literal("summary"), text: z.string().nullable() });

// ── 元素联合：判别联合（固定）+ 自由兜底 ──
const elementSchema = z
  .discriminatedUnion("label", [nameElement, dueDateElement, summaryElement])
  .or(baseElementSchema)   // 自由元素：label 任意
  .refine(自由元素的 label 不在 FIXED_LABELS 内);   // 防冒名（见 §三）
```

**「定死」的三个层次**（一次 extend 全中）：

| 层 | 由谁定死 |
|----|---------|
| 是哪种元素 | `label: z.literal("dueDate")` |
| text 是什么类型 | `text: localWallClockSchema.nullable()`（编辑器里 `el.text` 就是 `string\|null`） |
| 运行时格式 | 同一个 schema 的 `.parse()` 自动校验（**类型即校验**） |

**两层，不设中间层**（用户 2026-09-25 定）：根本 → 具体，直接 extend。

### 固定元素（唯一权威）

| label | text 类型（zod 收窄） | 必填 | 挂证据 |
|-------|---------------------|------|--------|
| `name` | `z.string().min(1)` | ✅ | ✅ |
| `dueDate` | `localWallClockSchema.nullable()` | ❌ | ✅ |
| `summary` | `z.string().nullable()` | ❌ | ✅ |

**加一个固定元素 = 加一行 extend + 更新 `FIXED_LABELS`**（§三的维护规则）。

### 自由元素

- label 模型自拟（"链接"/"地点"/"材料"…），**不设枚举**（「入口/材料/步骤」降级为惯例词，原 D-63）
- `text: string`（**无法收窄——本质如此**：一段人话）
- 可挂证据（`元素:<label>`）
- **label 不得与 FIXED_LABELS 冲突**（refine 强制）

### 类型即校验（用户 2026-09-25 定）

`localWallClockSchema` 等 zod schema **同时是类型定义和运行时校验**：

- **围栏不再手写格式正则**（原 `isLocalWallClock` 消失）——LLM 产出过 `ChangeListSchema.parse()` 时自动校验
- 改格式只改一处 schema（编译期与运行时同源，不会两处不一致）

### 变数拿到内部（用户 2026-09-25 定）

**schema 家族是「内部实现」**，外部只依赖两样：`elementSchema`（+ 推导出的 `Element` 类型）与存取函数。内部变数不外露：

| 变数 | 藏哪 |
|------|------|
| 固定元素名的集合 | 模块内常量 `FIXED_LABELS` |
| 判别联合的成员 | 模块内组装（外部只见 `elementSchema`） |
| 后续加/改固定元素 | 模块内加一行 extend（外部零改动） |
| 渲染顺序 | 从 `FIXED_LABELS` 派生（不手写第二份） |

**判据**：换一个内部实现（如把固定元素从 extend 改成别的写法）→ 只动这一个模块，外部契约不变。

### 独立字段（不是元素，不挂证据）

| 字段 | 类型 | 理由 |
|------|------|------|
| `tags` | `string[]` | 归类判断；来源是"打标签动作"（进 replay），非原文 |
| `status` | `"todo" \| "done" \| "archived"` | 处置状态；archived 于 D-83 启用，shelved 仍预留 |
| `doubtNote` | `string \| null` | 存疑标记（⚠️ D-85 起停新增——拿不准改入存疑信息库 §十一，字段保留兼容存量） |

**行级派生字段**（挂在看板行 ItemRow 上，不进 Item 快照/版本链；D-83 二轮）：`completedAt`（最近一次进入已完成的时刻——done 段排序与完成淡出梯度）与 `viewed`（是否已被用户打开过——存 `item_views` 表，「新」微标点开即消）。

ChatRequest.mentions（@ 提及）：`{ id, title }` 数组，**上限 8**（防超大数组直灌提示词）；服务端注入本条用户消息做指代消解。

**判据（硬）**：需要挂**原文依据**吗？需要 → 元素；不需要 → 独立字段。

## 五、依据（Basis）——统一的引用边

**所有依据 = `element → 目标`，subject 一律是 `元素:<label>`**：

```ts
Basis = { elementLabel: string, target: "原文快照" | "知识", pointer, capturedAt, capturedBy }
// subject 固定为 `元素:${elementLabel}`——固定元素与自由元素同一规则
```

**原三关注点的归属（用户 2026-09-25 定）**：

| 原关注点 | 现在挂在哪 |
|---------|-----------|
| `ddl` | 固定元素 `dueDate` 的证据（`元素:dueDate`） |
| `存在` | 固定元素 `name` 的证据（`元素:name`）——"这个事项存在"由语义名的原文依据支撑 |
| `归属` | **消失**——任务退场改标签，**标签不挂证据**（打标签动作进 replay）。故不再有归属证据 |

⚠️ **不再有裸名 subject**（原 `"存在"/"归属"/"ddl"` 逐个消解：前两个并入固定元素，第三个消失）。这是 Q19a「去枚举」的彻底完成。

**引用方向**：事项的元素 → 原文快照 或 知识，**单向**。

## 六、知识（Knowledge）——右侧节点（知识库落地时）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 主键 |
| `statement` | string | **原子一句话**（"英语课每周三上课"）——最低级知识 |
| `basis` | string \| null | 出处（原文快照指针） |
| `status` | `"有效" \| "依据已变更"` | |
| （不做） | — | 不做版本链；不做知识间引用；不做推理链 |

**对接面**（沿 D-52）：写口唯一（agent0「记知识」交说法+依据）；读口 `search_kb`；内部形态自由。
**引用方向**：事项 → 知识，单向；一个事项可依据多条知识。

## 七、明确「不做」（防扩散）

| 不做 | 原因 |
|------|------|
| 任务容器 / 任务树 / 嵌套 | 降级为标签，已由本契约取代 |
| 知识↔知识引用 | 只放最低级知识（用户定：知识库变得"平庸"是刻意的） |
| 推理链 / 持久化 DAG | 链是派生视图，不预建推理结构 |
| 可持久化数据结构（线段树/路径拷贝） | 规模不需要；用追加式版本链足够 |
| 知识版本化 | 选 b：改了扫引用者标「依据已变更」 |
| 时间旅行（任意历史状态回看） | 规格没要求；只有"单次撤回" |

## 十、改写纪律（强制，用户 2026-09-25 定）

> **每次改写契约后，必须重审「旧制度是否清理干净、新制度是否完全实施」——不许新旧并存。**

**每次改写的收尾动作**（不可省）：

1. **扫旧概念残留**：`grep` 旧术语（task/任务/事件/taskId/关注点/裸名 subject/旧字段名），逐个确认是「迁移对照」还是「真残留」
2. **验新制度落地**：新概念的**每一处引用**都符合契约（如：证据 subject 一律 `元素:<label>`，无裸名）
3. **跨文件一致**：00 契约 → 01 规格 → 02 台账 → 03 问题 → 04 验收 → CLAUDE.md → 代码，全部同步
4. **代码无逃逸**：不新增类型绕过（红线）；旧函数/字段删净（`knip` 零死代码）

**为什么强制**：本项目已多次吃「新旧并存」的亏（`hangings`→`elements` 留旧字段；`EvidenceSubject` 枚举删了注释没更新；事务传错句柄）。新旧并存 = 两套真相 = 静默失效的温床。

## 十一、进站批次与信源数据（信源阶段，D-84/D-85）

### RawInput（进站批次）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 主键（uuid） |
| `content` | string | 原始文本，永不丢失 |
| `sourceType` | string | chat / paste / nc / … |
| `sourceIdentity` | **对象（弹性字典）** | **core 契约只约束是对象 + 保留键 `sourceLabel`（非空，D-88 由 name 改名）**；适配器自由扩展其余键，整体 `JSON.stringify` 进 agent0 提示词。DB 存 JSON 串；存量字符串迁移为 `{sourceLabel: 原串}` |
| `receivedAt` | string | 接收时间（本地墙钟） |
| `eventTime` | string \| null | 事件时间；nc 等自带时刻的信源用它（比到达真实，与 receivedAt 的差距本身是信息） |
| `digestState` | `"pending" \| "digesting" \| "digested" \| "failed"` | 消化状态（digesting = 已发射消化未完成；孤儿由启动清扫归 failed，specs/004） |
| `raw`（仅 DB） | string \| null | 信源原始载荷 JSON 留底（nc 事件原文，图片段 base64 不进库）；**shared 的 RawInput 类型不含此字段**（归档用，agent0/web 均不消费） |

### source_settings（信源设置 KV）

```sql
CREATE TABLE source_settings (
  source TEXT NOT NULL,           -- 信源名（nc / …）
  key    TEXT NOT NULL,           -- 信源自定义（groups 白名单 / windowMinutes 窗长 / …）
  value  TEXT NOT NULL,           -- JSON 串
  PRIMARY KEY (source, key)
);
```

core 只管存取不解释内容（SourceContext.setSetting/getSetting，ctx 无 db——低耦合红线，D-84）。

### uncertain_inputs（存疑信息库，D-85）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 主键 |
| `content` | string | 原话逐字 |
| `sourceType` | string | 同 RawInput |
| `sourceIdentity` | 对象（JSON 串存） | 信源快照（供接近度匹配：同群/同发信人） |
| `eventTime` / `receivedAt` | string \| null / string | 时刻随条目暴露给 AI（无机械保质期的前提） |
| `originRawInputId` | string \| null | 从哪个批次摘出（可回溯原文） |
| `needsHuman` | int 0-100 | agent0 打的「需人工分」（人工通道按它倒序） |
| `reason` | string | 一句理由（缺什么信息/官方性/能否定量的语义在此） |
| `status` | `"open" \| "merged" \| "discarded"` | 状态变更全由判断触发（AI 或人工），无一由时钟触发 |
| `resolvedRef` | string \| null | 升格去向（merged 时的事项/批次 id） |
| `createdAt` / `resolvedAt` | string / string \| null | |

**ChangeItem 词表随 D-85 变化**：`+park_uncertain({content, needsHuman, reason})`、`+resolve_uncertain({id, outcome: merged|discarded, note, resolvedRef?})`、`-mark_doubt`（resolve_doubt 保留作存量消化出口）。
