## 一、我们做了什么

这是一个**个人自用的信息汇总工具**。使用者只有我本人（及少数几位家人朋友），不是对外经营的客服系统，也没有任何商业服务。

它的工作方式：

1. 我用自己的企业微信客服账号接收咨询消息；
2. 通过官方 API（`kf/sync_msg`）拉取这些消息；
3. 把消息汇总进我自己的备忘/待办清单，方便我统一查看"谁找过我、说了什么"；
4. 收到消息时，通过官方 API（`kf/send_msg`）回一句「信息已收到」，让发消息的人知道消息没丢。

**没有做的事**：没有群发营销、没有诱导分享、没有批量加好友、没有采集通讯录、没有把任何数据对外提供或出售、没有接入任何非官方工具或模拟客户端。

## 三、关于可能触发风控的行为（我们的问题）

我们复盘后，认为以下两点可能被系统判定为异常，**这是我们理解不足造成的，现已全部停止**：

**1. 回执频率过高**

为验证链路是否通畅，我们在短时间内把自动回执的间隔调到了很低的水平（6 秒），并连续测试了数次，导致同一个客户在短时间内收到多条机器生成的回执。

**这是测试行为，不是持续运营行为。** 我们已经把回执间隔恢复为保守值，并会保持在合理范围内。

**2. 会话状态的自动流转**

当客户会话处于「待接入池排队中」状态时，微信不允许 API 发送消息。我们为了让客户能收到"已收到"的回执，写了一段自动把会话转入人工接待、再结束会话的逻辑，使客户的下一条消息重新回到「未处理」状态。

我们现在意识到：**这种做法在效果上是在规避平台对会话状态的管理规则**，即使每一次 API 调用本身都在文档允许的范围内。这不符合平台设计该状态机的初衷，我们已停止这一行为。

## 四、我们准备做的整改

1. **停止自动结束会话**：不再通过状态流转绕开会话限制。若客户会话处于不可回复状态，我们就不回复，只做消息收录。
2. **回执频率回落**：回执间隔设为保守值（不低于 10 分钟），确保不会对任何客户形成高频机器消息。
3. **回执内容明确**：回执仅为「信息已收到」这类确认，不包含任何营销、推广、链接或引导分享的内容。
4. **数据仅自用**：客户消息仅存储在我本人的设备上，不向任何第三方提供、不用于任何商业用途。
5. 如平台认为自动回执本身不适宜，我们可以**完全关闭回执**，只保留消息读取与个人汇总。
