# 11 · 上云与发布（国内境内部署 · 从 0 到上线的全流程清单）

> 性质：**长期有效的操作清单**（与 07/08/09 同级）。目标 = 把这套系统以**多用户**形态部署到国内公网，供小圈子使用（现阶段的注册机制 = 邀请制）。
> 用法：逐项勾选、慢慢磨上线；每完成一项在本档打勾并记日期。凡标【决策】的先拍板再动手。
> 前置依赖：多用户功能（每用户一库 / 邀请制 / 会话 / 信源 token / 自带 key——见 03「下一阶段方向」）尚未立项开发；本档许多项**可与开发并行**准备。
> 沿革：2026-10-10 由用户提出并成文；同日对照「标准产品上多用户/上线流程」二次梳理——补 16 项（标【补】）、决策点扩至 9 个；**同日晚 9 个决策点全部拍板**（结论见各条与文末总表；另拍两条附带项：服务定位表述、产品对外名时机）。

## 阶段 0 · 顶层决策与承诺（先拍板，后续全依赖它）

- [x] 【决策】①**公网形态 = A（国内云 + 域名 + ICP 备案）**（2026-10-10 拍板）：服务器（阿里云轻量 2C2G）与**域名已自备**；**ICP 备案未办**（用户：「网站晚些时候再备」）——上线前必办（排队 2~4 周），备案需先定「网站名称」（见下条对外名）。B（香港）/ C（组网直连）均放弃，不走组网过渡。
- [x] 【决策】**服务定位表述**（2026-10-10 拍板）：**开源项目**（用户机制暂时一并开源）；托管服务**现阶段邀请制注册**（邀请制 = 目前的注册机制，非产品定义的永久边界）；**以后考虑 AI 服务之类的付费**配套。合规留意：不公开宣传为「AI 生成服务」（生成式 AI 面向公众服务有备案要求；自带 API key 模式把生成服务提供者角色推给用户，边界更干净）。
- [ ] 【补】**产品对外名 + 一句话介绍**（2026-10-10：域名已备、网站晚些再备——名字在**网站备案 / 公告前**定，届时碰候选）。
- [x] 【决策】③首批规模 = **3~5 个熟人**内测（2026-10-10 拍板；先自己用一周，再邀、观察一周再扩）。
- [ ] **隐私说明**（2026-10-10 ④ 拍板：**并入《简单协议》一份**，不单独成页）——PIPL 告知-同意的最小实践：收什么（用户自己录的信息）、存哪（本服务器、不共享不画像）、怎么删（注销 = 删库）、运维方能看到什么（如实写：库文件在服务器上，运维方技术上可见——「便利托管」而非「零信任」）。
- [x] 【补】【决策】⑦**免费边界 = 开源；除配套付费服务外免费**（2026-10-10 拍板）——公告与 README 口径按此写；未来付费仅限配套服务类（如 AI 服务），届时单独公告。
- [ ] 【补】**服务预期口径**：无 SLA、尽力而为、停服必提前公告（先说好比事故时解释便宜）。
- [ ] 【补】**免责声明**：AI 处理结果不保证正确——「帮你记，不替你判断」，与产品哲学一致，条款中写明。
- [x] 【补】【决策】⑨**用户数据导出承诺 = 暂不承诺**（2026-10-10 拍板）。连带：阶段 3「导出端点」、阶段 4「导出入口」两条**缓**；阶段 5 停服预案不再引用「导出可用」。
- [x] 【决策】④对外措辞（2026-10-10 拍板）：**如实写，放进一份《简单协议》正文**（协议正文含：收什么 / 存哪 / 怎么删 / 运维可见与否，如实交代）。开源与自部署包（`npm run build:release` 已有）本身即分流通道，不另做话术。

## 阶段 1 · 基础设施（可与开发并行）

- [x] 【决策】②**云服务器 = 阿里云轻量 2C2G**（2026-10-10：**用户已自备**；SQLite 多库 + Node 单进程，几十用户足够）。
- [x] 买**域名**（**用户已备**）；DNS 解析到服务器——**待接**。
- [ ] **ICP 备案**：**未办**（2026-10-10 澄清：域名已备，「网站晚些时候再备」）——**上线前必办**（排队 2~4 周）；备案需「网站名称」（先把对外名定了）。流程：云厂商备案系统提交（个人主体 / 身份证；网站名称规避「论坛、社区」类字眼与敏感词）→ 厂商初审 → 管局审核（各省 5~20 个工作日）→ 备案号挂页脚。
- [ ] **公安联网备案**（开服后 30 日内；备案流程的下一站，别忘）。
- [ ] **TLS**：Caddy 自动证书（Caddyfile 反代 3001，约十行）或云厂商免费证书（备案域名）。
- [ ] **服务器加固**：防火墙只开 80/443/SSH；SSH 改密钥登录 + 非标端口 + fail2ban；关掉一切不用的服务。
- [ ] **备份**：cron 快照 `data/`（多用户后 = 整目录；SQLite 用 `.backup` API 而非直接拷贝）+ 异地份（对象存储或定期拉回）；**做一次「试恢复」演练**才算完成。
- [ ] 【补】**告警通道**：证书续期失败 / 磁盘 / 进程存活 / 错误率——一个能叫醒你的机制（邮件即可；单人运维的底线）。
- [ ] 【补】**依赖安全**：开启 GitHub Dependabot + 上线前 `npm audit` 过一遍。
- [ ] 【补】**密钥细则**：服务器 `.env` 权限收紧 + 轮换策略（LLM key 用户自带；服务器侧主要是会话密钥/管理员凭据）；**日志规范**：保留期 + 日志不落用户正文。

## 阶段 2 · 部署形态与版本管理（代码侧，上云前做完）

- [ ] **Docker 化**：Dockerfile（node 单进程 + 前端静态合并已有）+ docker-compose（app + caddy + `data/` 卷）。发布两路：镜像（服务器用）与便携包 zip（自部署用户用，已有）。
- [ ] **CI**：GitHub Actions 在 tag 时跑 `npm run check` 并产出制品（国内拉取慢：镜像可推国内 registry，或在服务器上 build）。
- [ ] **版本管理规范**（0.x 阶段）：
  - [ ] 语义化 tag（`v0.x.y`），**部署只跟 tag 不跟 main HEAD**；
  - [ ] `CHANGELOG.md`（中文、按版本累计；与 GitHub Release 说明同源）；
  - [ ] GitHub Release 附件挂便携包 + 中文说明（v0.1.0 已有先例）。
- [ ] **数据库 schema 迁移**（上云前必补；多用户后 = 遍历所有用户库）：schema 版本号 + 启动时逐库迁移 + **迁移前自动备份**；明确「**迁移仅向前，回滚 = 恢复备份 + 回滚镜像 tag**」。
- [ ] **升级 runbook 成文**：备份 → 拉新镜像 → 迁移 → 健康检查 → 失败则回滚。
- [ ] 【补】**升级脚本化**：runbook 收敛成一条可执行脚本（人工步骤最小化）。
- [x] 【补】【决策】⑥**预发环境 = 本地全绿 + 服务器自用灰度一天**（2026-10-10 拍板；不搭 staging）。
- [ ] 【补】**负载冒烟**：上线前 wrk/ab 打基础量，确认单进程扛得住预期用户数。
- [ ] **服务器初始化脚本**：装 docker/防火墙/cron 一条龙，换机可重来。

## 阶段 3 · 多用户功能（前置开发，spec-kit 立项）

- [x] 【决策】⑤多用户立项时点 = **直接立项**（2026-10-10 拍板；加源顺延）——按 03「下一阶段方向」极小集开工：每用户一库（`data/users/<uid>.db`）/ 邀请制注册 + 密码 / 会话层（`makeApp` 请求期解析 db）/ 信源 webhook 带用户 token / 每人自带 LLM key。**下一步工作 = spec-kit 立项**。
- [ ] 明确不做（本阶段红线）：协作、共享、公开注册、计费、跨用户检索。
- [ ] 管理员面（极简即可）：邀请码生成、用户列表、停用账号——CLI 或一页 admin。
- [ ] 【补】**安全细则成条目**：argon2 哈希、登录限速/爆破锁定、会话 cookie（httpOnly/SameSite/过期）、邀请码一次性 + 有效期、注册限速。
- [ ] 【补】**数据导出端点**——**缓**（2026-10-10：⑨ 暂不承诺导出）：每个用户可导出自己的全部数据（与阶段 0 决策⑨对应）。
- [ ] 【补】**数据保留 SLA**：注销后 N 天真删 + 备份中的残留保留期——对用户明示。
- [ ] 【补】**数据泄露应急**：发现 → 通告用户 → 修复的流程与时限（小规模也要有，诚实承诺）。

## 阶段 4 · 公告与运营面（上云前必须有）

- [ ] **公告系统**：站内公告（顶部横幅；一张表或一个 JSON + 管理入口）。用途 = 维护窗口、版本更新、服务调整——**只被动展示、零推送**（延续 01§8.2 反打扰纪律）。
- [ ] **更新日志页**：从 CHANGELOG/Releases 渲染进站内（用户可见「这版加了什么」）。
- [ ] **首登引导**：欢迎 → 配自带 key（测试连接已有）→ 接第一个信源 → 完成。
- [ ] **《简单协议》成文页**（2026-10-10 ④ 拍板：服务条款 + 隐私说明 + 免责声明合为**一份简单协议**；阶段 0 起草）。
- [ ] **反馈渠道**：一个邮箱或站内一个入口；**不开 IM 群**（个人运营的管理成本）。
- [ ] 【补】**反馈闭环**：收到 → 处理 → 变更进更新日志（闭环才叫渠道）。
- [ ] `robots.txt` 全站 noindex（小圈子服务不希望被收录）+ 未登录只剩登录页。
- [ ] 【补】**帮助/FAQ 页**（怎么配 key、怎么接信源——减支持负担）。
- [ ] 【补】**数据导出入口**放用户侧可见处（与阶段 3 对应）——**缓**（2026-10-10：⑨ 暂不承诺导出）。

## 阶段 5 · 上线流程（runbook）

- [ ] 上线前总检：全量测试绿 / TLS 有效 / 备份 + 恢复演练过 / 公告就位 / 《简单协议》页就位 / 注册邀请开关默认关 / 404 与 500 兜底页。
- [ ] 【补】**UAT**：用户视角剧本走一遍——注册 → 配 key → 接信源 → 收消息 → 看板 → 流水 → 存疑 → 对话。
- [ ] 上线日：自己先用一周 → 邀首批 **3~5 个熟人**（③，先邀 1~2 也行）→ 观察（错误日志、磁盘、备份成功）→ 逐步扩大。
- [ ] 事故预案写下：挂机公告模板、联系渠道、回滚步骤（照阶段 2 runbook）。
- [ ] 【补】**回滚真演练一次**（不能只写在纸上）。
- [ ] 【补】**停服预案**：提前 30 天公告（2026-10-10：⑨ 暂不承诺常态导出——「不干了数据怎么交还」出预案时再定）。

## 阶段 6 · 持续运营

- [ ] 发布节奏：小步快跑（1~2 周一个 tag），每次发布在公告里留一行。
- [ ] 每月：备份恢复演练一次 + 磁盘/成本检查；每季：依赖升级（`npm outdated` 过一遍）。
- [ ] 成本台账（服务器 + 域名约每年数百元量级，记账即可）。
- [ ] 【补】**运营指标（克制版）**：只看技术面（错误率/用量/备份成功率）；**不做用户行为画像**（延续产品纪律）。
- [x] 【补】【决策】⑧**容量阈值 = 不设硬线**（2026-10-10 拍板）：文档建议档（磁盘 70% 告警 / 85% 升配、CPU 持续 80% 升配、用户 ~30 复核）先挂参考，真到量再修。用户备注：2G 指**内存**（文本数据量极小、轻量磁盘富余——磁盘不是约束，约束在 CPU/内存）。
