# 11 · 上云与发布（国内境内部署 · 从 0 到上线的全流程清单）

> 性质：**长期有效的操作清单**（与 07/08/09 同级）。目标 = 把这套系统以**多用户**形态部署到国内公网，供邀请制的小圈子使用。
> 用法：逐项勾选、慢慢磨上线；每完成一项在本档打勾并记日期。凡标【决策】的先拍板再动手。
> 前置依赖：多用户功能（每用户一库 / 邀请制 / 会话 / 信源 token / 自带 key——见 03「下一阶段方向」）尚未立项开发；本档许多项**可与开发并行**准备。
> 起点（2026-10-10）：由用户提出，先成清单，慢慢磨。

## 阶段 0 · 顶层决策（先拍板，后续全依赖它）

- [ ] 【决策】**公网形态三选一**：
  - **A. 国内云主机 + 域名 + ICP 备案**（合规正道；备案 2~4 周、个人可办；面向国内用户的最稳路）
  - **B. 香港/境外轻量服务器 + 域名**（免备案、当天可上线；但大陆访问质量赌线路、面向国内用户属合规灰区，仅宜极小圈子试水）
  - **C. 暂不理公网：Tailscale/组网直连**（零合规成本、零暴露面；推广 = 给熟人装客户端——最保守的起点）
  - 建议路径：**C 先跑通多人试用（现在就能做，代码注释里已留 Tailscale 场景）→ 同步启动 A 的备案（排队最久，别等开发完成才办）→ 备案下来切公网**。
- [ ] 【决策】**服务定位表述**：只做「邀请制的个人信息助手」，**不公开宣传为 AI 生成服务**（生成式 AI 面向公众服务有备案要求；用户自带 API key 模式把生成服务提供者角色推给用户，边界更干净——这是自带 key 的又一条理由）。
- [ ] 【决策】首批规模：建议 3~5 个熟人内测，观察一周再扩。
- [ ] 写一页**隐私说明**（PIPL 告知-同意的最小实践）：收什么（用户自己录的信息）、存哪（本服务器、不共享不画像）、怎么删（注销 = 删库）、运维方能看到什么（诚实：库文件在服务器上，运维方技术上可见——「便利托管」而非「零信任」，这条要如实写）。
- [ ] 【决策】「运维可见库文件」的对外措辞定稿（或对数据敏感者推**自部署便携包**分流，已有 `npm run build:release`）。

## 阶段 1 · 基础设施（可与开发并行）

- [ ] 买**云服务器**：国内轻量（腾讯云/阿里云轻量 2C2G 起步；SQLite 多库 + Node 单进程，几十用户足够）；地域选离主要用户近的。
- [ ] 买**域名**（.com/.cn 均可，需实名）；DNS 解析到服务器。
- [ ] **ICP 备案**（A 方案时）：云厂商备案系统提交（个人主体 / 身份证；网站名称规避「论坛、社区」类字眼与敏感词）→ 厂商初审 → 管局审核（各省 5~20 个工作日）→ 备案号挂页脚。
- [ ] **公安联网备案**（开服后 30 日内；备案流程的下一站，别忘）。
- [ ] **TLS**：Caddy 自动证书（Caddyfile 反代 3001，约十行）或云厂商免费证书（备案域名）。
- [ ] **服务器加固**：防火墙只开 80/443/SSH；SSH 改密钥登录 + 非标端口 + fail2ban；关掉一切不用的服务。
- [ ] **备份**：cron 快照 `data/`（多用户后 = 整目录；SQLite 用 `.backup` API 而非直接拷贝）+ 异地份（对象存储或定期拉回）；**做一次「试恢复」演练**才算完成。

## 阶段 2 · 部署形态与版本管理（代码侧，上云前做完）

- [ ] **Docker 化**：Dockerfile（node 单进程 + 前端静态合并已有）+ docker-compose（app + caddy + `data/` 卷）。发布两路：镜像（服务器用）与便携包 zip（自部署用户用，已有）。
- [ ] **CI**：GitHub Actions 在 tag 时跑 `npm run check` 并产出制品（国内拉取慢：镜像可推国内 registry，或在服务器上 build）。
- [ ] **版本管理规范**（0.x 阶段）：
  - [ ] 语义化 tag（`v0.x.y`），**部署只跟 tag 不跟 main HEAD**；
  - [ ] `CHANGELOG.md`（中文、按版本累计；与 GitHub Release 说明同源）；
  - [ ] GitHub Release 附件挂便携包 + 中文说明（v0.1.0 已有先例）。
- [ ] **数据库 schema 迁移**（上云前必补；多用户后 = 遍历所有用户库）：schema 版本号 + 启动时逐库迁移 + **迁移前自动备份**；明确「**迁移仅向前，回滚 = 恢复备份 + 回滚镜像 tag**」。
- [ ] **升级 runbook 成文**：备份 → 拉新镜像 → 迁移 → 健康检查 → 失败则回滚（镜像 tag + 备份恢复）。
- [ ] 服务器**配置管理**：密钥只存在服务器 `.env`（不进仓库不进镜像）；一份「服务器初始化脚本」（装 docker/防火墙/cron）防换机重来。

## 阶段 3 · 多用户功能（前置开发，spec-kit 立项）

- [ ] 按 03「下一阶段方向」的极小集开工：每用户一库（`data/users/<uid>.db`）/ 邀请制注册 + 密码 / 会话层（`makeApp` 请求期解析 db）/ 信源 webhook 带用户 token / 每人自带 LLM key。
- [ ] 明确不做（本阶段红线）：协作、共享、公开注册、计费、跨用户检索。
- [ ] 管理员面（极简即可）：邀请码生成、用户列表、停用账号——CLI 或一页 admin。

## 阶段 4 · 公告与运营面（上云前必须有）

- [ ] **公告系统**：站内公告（顶部横幅；一张表或一个 JSON + 管理入口）。用途 = 维护窗口、版本更新、服务调整——**只被动展示、零推送**（延续 01§8.2 反打扰纪律）。
- [ ] **更新日志页**：从 CHANGELOG/Releases 渲染进站内（用户可见「这版加了什么」）。
- [ ] **首登引导**：欢迎 → 配自带 key（测试连接已有）→ 接第一个信源 → 完成。
- [ ] **服务条款 + 隐私说明**页面（阶段 0 起草的成文）。
- [ ] **反馈渠道**：一个邮箱或站内一个入口；**不开 IM 群**（个人运营的管理成本）。
- [ ] `robots.txt` 全站 noindex（小圈子服务不希被搜索引擎收录）+ 未登录只剩登录页。

## 阶段 5 · 上线流程（runbook）

- [ ] 上线前总检：全量测试绿 / TLS 有效 / 备份 + 恢复演练过 / 公告就位 / 条款隐私页就位 / 注册邀请开关默认关 / 404 与 500 兜底页。
- [ ] 上线日：自己先用一周 → 邀 1~2 个内测熟人 → 观察（错误日志、磁盘、备份成功）→ 逐步扩大。
- [ ] 事故预案写下：挂机公告模板、联系渠道、回滚步骤（照阶段 2 runbook）。

## 阶段 6 · 持续运营

- [ ] 发布节奏：小步快跑（1~2 周一个 tag），每次发布在公告里留一行。
- [ ] 每月：备份恢复演练一次 + 磁盘/成本检查；每季：依赖升级（`npm outdated` 过一遍）。
- [ ] 成本台账（服务器 + 域名约每年数百元量级，记账即可）。

## 决策点汇总（用户逐条拍板）

1. A/B/C 公网形态（建议：C 起步 → A 收口，备案现在就可以开始排队）
2. 域名与服务器厂商、地域
3. 首批邀请人数与名单
4. 「运维可见库文件」的对外措辞（或对敏感用户推自部署包）
5. 多用户开发的立项时点（加源之前还是并线）
