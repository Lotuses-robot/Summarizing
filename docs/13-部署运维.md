# 13 · 部署与运维（升级 runbook + 服务器初始化）

> 性质：**长期有效的操作手册**（与 07/08/09/11/12 同级）。批次 2「代码侧上云项」产物之一（docs/11 阶段 2）。
> 前置：docs/11 阶段 0/1 的决策（形态 A 国内云、阿里云轻量 2C2G、Docker 部署、数据 bind mount）。
> 本文档给**可执行**的步骤——能脚本化的都在 `scripts/`（`server-init.sh` / `upgrade.mjs`）。

## 一、服务器初始化（新机一条龙）

`scripts/server-init.sh`（在服务器上以 root/sudo 跑一次）：装 Docker + 防火墙只开 80/443/SSH + 开 swap + 建 `data/` 目录并设属主。
细节与手工步骤见脚本头部注释；这里只记**为什么**：

- **swap 1~2G**：构建/消化有内存尖峰，2G 内存机器配 swap 作 OOM 保险（docs/11 阶段 1）。
- **data/ 属主**：容器内以 uid 1000 的 node 用户运行，宿主机 `./data` 必须可写——否则首启 `SQLITE_CANTOPEN`（Dockerfile 注释 / docs/11 部署注意）。
- **防火墙只开 80/443/SSH**：应用端口（3001）绝不直暴公网，TLS 唯一入口是 Caddy（`docker-compose.yml` 刻意不给 app 映射端口）。

## 二、首次部署

```bash
# 1. 拉代码 / 或用 CI 推的镜像
git clone <repo> && cd summarizing-public   # 或只放 docker-compose.yml + Caddyfile + .env
cp .env.example .env                         # 按需改 PORT/TRUST_PROXY 等（AI key 不在 .env——每账户在设置里配）
# 2. 起服务（本地 build 或 image: 指向 CI 推的 ACR 镜像）
docker compose up -d --build
# 3. 建第一个账户（邀请制注册前的引导）
docker compose exec app node apps/server/dist/admin.mjs user:add 你的名字
# 4. 发邀请码（给熟人）
docker compose exec app node apps/server/dist/admin.mjs invite:new
```

验证：浏览器访问域名能登录；`docker compose ps` 两个容器 healthy。

### 2.1 用 CI 构建的镜像（阿里云 ACR）——可选，服务器不 build

首版可直接在上面的 `--build` 形态跑（服务器本地构建，零 registry）。当构建变慢/内存吃紧时，改用
「CI 出镜像 → 服务器只 pull」，容器镜像服务用**阿里云 ACR 个人版（免费）**：

1. **ACR 控制台**（https://cr.console.aliyun.com/）→ 建**个人实例** → 设 Registry 登录密码（用户名默认账号全名）。
   - ⚠️ 该密码独立于阿里云登录密码，专供 `docker login`。
2. 建**命名空间**（如 `lotuses`）+ **镜像仓库**（名 `summarizing`，**私有**）。
   - ⚠️ 仓库创建时选 **「不自动构建」**——构建交给 GitHub Actions，别让阿里云也 build 一份（两套真相 + 触发时机按 push 而非 tag）。
3. 记下仓库**公网地址**——**新版个人版是每实例专属域名**，形如
   `crpi-<实例id>.<地域>.personal.cr.aliyuncs.com`（旧文档里 `registry.cn-<地域>.aliyuncs.com` 是过时格式，别用）。
   **地域选与服务器同地域**（服务器拉取可走「专有网络」地址 `<实例id>-vpc.<地域>.personal.cr.aliyuncs.com`，快且免公网流量）。
   ⚠️ **Secret 里填纯域名**（不带 `https://`、不带尾斜杠）——2026-10-12 实测：`docker login` 会容忍前缀，
   但拼进镜像 TAG 会让推送目标变形报 `denied`（CI 已就地规范化，但 secret 干净最省事）。
4. 在 GitHub 仓库 `Settings → Secrets and variables → Actions` 配 4 个 secret（名字一字不差）：
   `ACR_REGISTRY` / `ACR_NAMESPACE` / `ACR_USERNAME` / `ACR_PASSWORD`。
5. 打 tag 触发 CI 出镜像：`git tag vX.Y.Z && git push origin vX.Y.Z` → `release.yml` 的 `image` job 构建并推 ACR。
6. 服务器 `.env` 里设 `APP_IMAGE=<ACR_REGISTRY>/<ACR_NAMESPACE>/summarizing:vX.Y.Z`，然后：
   ```bash
   docker compose pull && docker compose up -d --no-build   # 只拉不 build
   ```
   （`docker-compose.yml` 的 `image:` 读 `APP_IMAGE`，缺省 `summarizing:local` = 本地 build 形态。）
   > 之后升级不必手改这一行——`npm run upgrade` 会把 `APP_IMAGE` 自动改到目标 tag 再拉取（见 §三）。

## 三、升级 runbook（**核心**）

> 原则：**迁移仅向前**；回滚 = 恢复备份 + 回退镜像 tag（docs/12 五）。升级前**必做备份**。
> `npm run upgrade`（= `scripts/upgrade.mjs`）把下面步骤脚本化：**查最新版 → 核对 ACR 已同步 → 备份 → 改写 .env 到目标 tag → 拉镜像 → 重启迁移 → 健康检查**；
> 手工步骤在此逐条列出以便理解脚本在干什么。

0. **版本核对（脚本第 0 步，仅 ACR 形态）**：读 GitHub `releases/latest`（发布源头；`gh` 不可用自动回退 `curl` 公开
   API，都不可用/限流时可 `UPGRADE_TARGET=vX.Y.Z` 手动指定目标）→ 比对**当前在跑容器的镜像 tag**（`.env` 声明值
   仅作后备——「.env 已改但还没 pull」不会被误判成已最新）→ **用 `docker manifest inspect` 确认 ACR 已有该 tag**——
   没有则**显式拒绝**（CI 可能还在构建/失败，或服务器未 `docker login` ACR），绝不冒险拉到旧镜像；目标比当前旧则**拒降级**。本地 build 形态无 tag 可比，跳过此步。
   ```bash
   node scripts/upgrade.mjs   # 打印「当前 vX → 最新 vY」；已最新则退出，未同步/降级则拒绝
   ```

1. **备份**（升级前，最重要的一步）——**在线热备，不停服**：
   ```bash
   # 容器内走 SQLite .backup API（WAL 安全、可并发读写）——逐库备 system.db + users/*.db；
   # 009 起 media/（图片字节）随库一起拷进备份目录（只备库不备图 = 还原后全是「图片已过期」）
   docker compose exec -T app node apps/server/dist/admin.mjs backup
   # → 默认落 data/backups/<北京戳>/（在挂载点内——容器重建也留得住）；再异地存一份（对象存储/拉回）
   ```
   `scripts/upgrade.mjs` 已把这一步自动化（第一步就是它；它用 `pre-upgrade-<戳>/` 子目录，每次升级互不覆盖）。
   ⚠️ 注意：**schema 迁移本身也会自动备份**（`migrate.ts`，落后版本首次开库时留一份 `<库>-v<旧版本>-<时间戳>.db` 到 `data/backup/`）——但那是应用进程内、迁移前的保底，**不能替代你升级前的人工备份**（两者互补）。

2. **改 .env + 拉新镜像 / 更新代码**：ACR 形态先把 `.env` 的 `APP_IMAGE` 改到目标 tag（脚本自动做——不改这行，
   `pull`/`up` 拿到的还是旧 tag），再 `docker compose pull`；本地 build 形态 `git pull` + `docker compose build`。

3. **重启触发迁移**：`docker compose up -d`。启动时 `makeRegistryDb` / `makeDb` 会对每个库过版本门控——落后则**先备份再迁移**（见 `migrate.ts`）。

4. **健康检查**：
   ```bash
   docker compose ps                                   # 两容器 healthy
   docker compose logs app | tail -50                  # 无 [schema] 报错、无 [space] 装配失败
   curl -fsS https://<域名>/api/board -o /dev/null -w '%{http_code}\n'   # 期望 401（未登录面）
   ```
   登录看板，确认数据在、新功能可用。

5. **失败则回滚**：
   - 回退镜像 tag：`docker-compose.yml` 的 `image:` 指回上一个 `vX.Y.Z` → `docker compose up -d`。
   - 若迁移已改库且需彻底回到旧结构：**停服**（`docker compose down`）→ 还原升级前备份：
     ```bash
     docker compose exec -T app node apps/server/dist/admin.mjs restore /app/data/backups/<戳>
     # <戳> = 升级前备份目录（upgrade 输出「本次升级前备份」一行里有）；覆盖 system.db + users/*.db + media/
     # 并清 -wal/-shm 残留（离线操作，务必先停服）
     ```
     → 用旧镜像起（`docker compose up -d`）→ 验证。

### 三·补、同一个 tag 重推了镜像，怎么让服务器换上

正常情况一个 tag 的镜像内容不变，所以 `npm run upgrade` 见「同 tag」就停（不折腾线上）。
但**镜像有 bug、修好后用同一个 tag 重推**时（v0.7.0 的 GLIBC 事故就是这种），需要显式重拉：

```bash
node scripts/upgrade.mjs --force     # = 删本地同名镜像 → pull → 备份 → 重建 → 健康检查
```

`--force` 的语义就是「不信本地这一份」。手工等价操作：

```bash
docker compose pull app && docker compose up -d
# 若 pull 认定「已是最新」不下载：先删掉本地那份再拉
docker rmi $(docker inspect --format='{{.Image}}' $(docker compose ps -q app))
docker compose pull app && docker compose up -d
```

⚠️ **CI 手动重推镜像时必须填 `image_tag`**（如 `v0.7.0`）：`workflow_dispatch` 的
`github.ref_name` 是**分支名**（`main`），不填会把镜像推成 `:main`，服务器按 `:v0.7.0` 永远拉不到。
没填现在会直接构建失败（含 `v` 前缀校验），不会静默推错。

## 四、日常运维

- **一屏诊断**：`npm run status` —— 容器状态 + 应用日志尾部错误 + 磁盘 + 最近备份 + 版本，出错时先敲它。
- **备份**（cron，docs/11 阶段 1）：定期 `docker compose exec -T app node apps/server/dist/admin.mjs backup`（在线 `.backup` API，不停服；默认落 `data/backups/<北京戳>/`，`--out` 可自定）+ 异地存；**做一次「试恢复」演练**才算完成——`npm run admin -- restore <DIR>` 还原（须先停服）。
  - 保留策略：迁移前备份自动保留最近 5 份（`migrate.ts`）；日常备份目录由你的 cron/异地脚本自行轮转（不要把备份堆在 `data/backups/` 里太久，随 data 一起越来越大）。
- **日志**：`docker compose logs`；Caddy 访问日志在 `caddy_data` 卷（`/hook` 已按 R12-2 跳过）。
- **账户运维**：`docker compose exec app node apps/server/dist/admin.mjs <命令>`（`user:add` / `invite:new` / `user:list` / 停启等，用法见命令不带参数时的帮助）。
- **告警**（docs/11 阶段 1 补）：证书续期失败 / 磁盘 / 进程存活——一个能叫醒你的机制。

## 五、状态监控与告警（Uptime Kuma，SSH 隧道访问）

单人运维，"出错时能最快定位 + AFK 时能被叫醒" = 一个网页面板。用 **Uptime Kuma**（最轻的在线监测面板，自带告警），
**只绑宿主回环 `127.0.0.1`、绝不暴公网**——访问走 **SSH 隧道**；`docker-compose.yml` 里 `uptime-kuma` 属 compose profile `monitor`（默认不起）。
**无需程序侧对接**：Kuma 是外部黑盒监测，它定时 HTTP 敲你已有的端点，服务端零改动。

1. 起面板：服务器上 `docker compose --profile monitor up -d`（它只监听 `127.0.0.1:3002`）。
2. **建 SSH 隧道访问**（本机跑，`-L` 把服务器回环 3002 映射到本地 3002）：
   ```bash
   ssh -L 3002:localhost:3002 admin@<服务器IP>     # 保持这个窗口开着
   ```
   *省事做法*：写进本机 `~/.ssh/config`（`Host <你的别名>` 下加 `LocalForward 3002 localhost:3002`）——以后 `ssh <别名>` 就自带隧道。
3. 浏览器开 `http://localhost:3002` → 首次建管理员账号。
4. 加**监测项**（这才是价值所在）：
   - **服务在线**：HTTP(s)，URL = `https://<你的域名>/api/board`，**期望状态码 401**（受保护面未登录应答 = 服务活着）。
   - **证书到期**：HTTP(s) 监测勾选「Expiry Notification」（证书快过期提前告警——Caddy 续期失败时唯一能叫醒你的信号）。
   - **磁盘**：配合一个 cron 脚本或 Uptime Kuma 的「Push」监测（自写脚本推 `df` 结果）。
5. 配**告警通道**（Notifications，Uptime Kuma 支持邮件/SMTP、Server酱、Telegram、Webhook…）——**至少配一个**，"能叫醒"才成立。

> **不用自建运维页**：命令行 `npm run status`（一屏诊断）+ 本面板（在线/告警）+ `docker compose logs`（细查）三者互补，够用。
> 更重的方案（Portainer 容器管理 / Grafana+Prometheus 指标）在 2C2G 上是负担，本项目规模不需要。

## 五·补、原生模块与基础镜像（v0.7.0 事故后加）

**规则：原生模块能不能用，由「目标镜像的 glibc」决定，不由「有没有预编译产物」决定。**

- v0.7.0 上线时 app 容器起不来，日志 `ERR_DLOPEN_FAILED: version GLIBC_2.38 not found`——
  nodejieba 的 linux-x64 预编译产物要求 GLIBC **2.38**，而 `node:22-slim` 是 Debian **bookworm（2.36）**。
  现基础镜像已升到 `node:22-trixie-slim`（Debian 13 / glibc **2.41**）。**不要图省事改回 `-slim`。**
- **Dockerfile 里有两道构建期冒烟**（构建阶段 + 运行阶段各一次 `require('nodejieba')` + `load()` + 真切一个词）。
  它们故意在构建时跑：本地 Windows 用的是 win32 产物，Linux 那半只有进容器才暴露——
  不要让这类错误重新等到服务器上 502。
- **升级基础镜像 / 换 Node 大版本时**：先看该原生模块在目标发行版上能否加载，别只看它「有没有 prebuild」。
  一次验证几分钟，事故是一次停服。

## 六、部署注意清单（R12，源自 specs/006 research）

- `TRUST_PROXY=1` 的前提：应用端口不直暴公网；XFF 由 Caddy 覆写为直连 IP（防伪造头绕限速）。
- 反代日志**不记 `/hook`**（令牌在路径里）。
- `data/` 目录权限：宿主机目录须 uid 1000 可写。
- 安全头与 CSP/HSTS：应用侧与 Caddy 侧各发一份。
- 反代层防护覆盖 `/hook`。
- **监控面板只绑宿主回环**（`127.0.0.1:3002`），访问走 SSH 隧道——那是运维入口，暴公网=送攻击面。
