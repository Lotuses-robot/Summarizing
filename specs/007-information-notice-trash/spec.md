# Feature Specification: 信息分流（通知类别）+ 回收站

**Feature Branch**: `007-information-notice-trash`

**Created**: 2026-10-16

**Status**: ✅ 已交付（2026-10-17；spec → plan → tasks 已走完，代码在分支 `007-information-notice-trash`，382 测试全绿；两个子系统拆分落地的边界见「交付拆分」）

**Input**: 用户原话与多轮澄清（2026-10-16）：
- "很多信息完全落在了事项上，混在一起了"——指非动作类通知被建成了没有日期的伪事项（躺在日期未知段）。
- 典型样本："数据结构课改到明理楼3楼"——**不是事项但要知道**，价值高、无 ddl。
- "干脆，继承事项的数据模型，在日期未知上方留一栏表示通知……或者给每个分区单独设 prompt" → 用户已否掉 per-partition prompt。
- 最终定形：**通知（丙：独立入口，套事项模板但 dueDate 不作为可选项）**＋**回收站（独立区域，非类型）**＋**分类整理为 信息 = 事项(三段) + 通知**＋**图标按 状态/事项/通知 重新斟酌**。
- "把 item 当信息点"——`Item` 作为信息的统一载体。
- 首条反馈（本批次想法的起点）："没有回收站会让垃圾事项堆成山"。
- 追加决策（2026-10-16）：「把『归档』的状态取消，只保留完成」——用户与使用者体验一致：归档与完成体感相近、几乎用不上；随通知/回收站本批一并落地（事项看板由四段收为三段，存量 archived 数据迁移为 done，见 FR-018）。
- "算了算了，item 先不改，但是 item 必须要改成 tasks"——命名澄清：统一载体名沿用 `Item`（全量换词延后，不在本批）；`kind` 取值定为 `task`（事项）/ `notice`（通知）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 通知：不进群也知道发生了什么 (Priority: P1)

我在意的群（已在 nc 白名单内）发来"课改到明理楼3楼""时间调到周五"这类**没有动作落点、我不需要去"做"但必须知道**的消息时，打开系统就能在一个**独立的「通知」入口**看到——不用去翻群。

**Why this priority**: 这是本批次的核心体验闭环（"不看群"）。做完系统立刻可用、可独立验收，且不依赖回收站。

**Independent Test**: 一条 nc 白名单群的非动作类消息进站 → agent0 判为通知 → 「通知」页出现该条（含来源徽标、时间、原文入口）；看板三段**不出现**它。

**Acceptance Scenarios**:

1. **Given** 群发来"数据结构课改到明理楼3楼"（无动作落点），**When** agent0 消化，**Then** 生成一条通知（kind=notice），出现在「通知」页；**且** 不进入看板的日期未知/已排期/已完成任一段。
2. **Given** 通知页有若干条通知，**When** 我打开，**Then** 每条显示 来源徽标（如 `[nc] 数据结构课群`）＋ 时间 ＋ 一句话内容；点开可见原文（复用现有证据/来源信息机制）。
3. **Given** 一条既有事项（有动作），**When** 同类消息再来，**Then** 仍走事项路径（去重合并），**不会**被误判成通知。
4. **Given** 一条新通知，**When** 我查看通知页，**Then** 它有「已读」状态（未读微标，点开即消，复用 `item_views`）；行右缘有**删除**按钮。
5. **Given** 一条通知，**When** 我删除它，**Then** 它进回收站（见 Story 3），从「通知」页消失但可复活。

### User Story 2 - 信息统一载体：一个 Item 同时装得下事项与通知 (Priority: P1)

底层只有一种"信息"（Item），事项与通知是它的两种 kind（`task`/`notice`）。事项有状态演化（todo/done；D-83 已归档本批取消，见 FR-018），必须有 ddl（可留空）；通知无 ddl、不参与"完成"演化。分类轴（kind）与演化轴（status）分离，治愈"日期未知段不对齐"。kind **可切换**（复用 `update_item`）：**唯一约束 = ddl 形状**（通知必无 ddl；事项必须有 ddl、可留空），**不做任何其他限制**。

**Why this priority**: 这是存储与类型的地基。Story 1 的"不污染看板"与 Story 3 的"通知也能进回收站"都依赖它。没有它，通知只能伪装成"没有 ddl 的 todo"，混在事项里。

**Independent Test**: 构造 kind=notice 的信息 → 版本链/证据/标签机器照常工作；schema 拒绝"给通知标 done"这类非法状态；看板派生正确排除 notice。

**Acceptance Scenarios**:

1. **Given** 一条通知（kind=notice），**When** 走版本链、证据、标签、来源信息，**Then** 与事项完全同构（复用同一套存储与 UI 模板）。
2. **Given** 一条通知，**When** agent0 或前端试图给它 `complete_item`，**Then** 被围栏拒绝（**按 `kind=notice` 判**——通知不参与完成演化；不靠 status 白名单，通知的 status 恒 todo）。
3. **Given** agent0 给一条通知产出了 `dueDate` 元素，**When** 过围栏，**Then** **整条拒收**（不剥离该元素部分接受）——通知不含 ddl 是结构红线；拒收走既有围栏流程（留痕、可修正重提），修正后重发不含 ddl 的通知（用户 2026-10-16 定，OQ-2）。
4. **Given** 一条通知，**When** 后续信息表明它其实有动作落点，**Then** agent0 可用 `update_item` 把 kind 切换为 `task`——**复用 update_item 承载切换，不新造动作**；**唯一校验 = ddl 形状**（task：必须有 ddl、可留空），**不做任何多余限制**（不因状态拒转）（用户 2026-10-16 定，U3）。
5. **Given** 一条通知，**When** 后续信息更新它（如地点再次变更），**Then** agent0 用 `update_item` 修改同一条通知（查询与修改都自然支持）；**不做通知↔事项的自动关联机制**（两条互不相干的条目各归各，用户 2026-10-16 定，U2）。
6. **Given** 一条通知，**When** agent0 判得出承载它的课程/归类，**Then** 给它打 tag；**判不出时 tag 留空**（不编造语义默认值——与事项同一条"结构容错≠语义兜底"红线）。tag 与事项**共用一套词**（同一个 tag 可同时挂在两类上——数据层留归类/筛选关联）；当前 UI **仅各视图内**过滤，不做跨视图聚合（见场景 7）。
7. **Given** 通知页，**When** 我在其中过滤，**Then** 与看板用**同一套筛选机制**（tag + 文本，复用现有 FilterBar 能力；**首版不做来源维度筛选**）——**不做全局跨入口搜索视图、不推翻三段看板**（用户 2026-10-16 定：相同部分照抄，不动太多刀；混排时间线/全局搜索等方案明确不做）。
8. **Given** 看板装配，**When** 库中同时有 task 与 notice，**Then** notice 不进看板任一段，只进「通知」页。
9. **Given** 一条已归档事项（存量，迁移前），**When** 本批迁移执行，**Then** 它的 status 变为 done、进入已完成段——归档不再是可派生的状态（见 FR-018）。
9. **Given** 「日期未知」段，**When** 查看其定义，**Then** 它 = `kind=task` 且 `status=todo` 且 dueDate 无值——是一个筛选视图，不是独立类型（现状不变，本特性不改它）。

### User Story 3 - 回收站：删了能复活，一键清 15 天前 (Priority: P2)

看板/通知页/对话里删除一条信息（行右缘按钮）→ 进回收站（独立入口，可复活）；回收站内**唯一**批量操作是「一键清理」——按下即彻底清除 trashed 超过 15 天的信息（**用户显式触发，不做自动定时清除；无「清空全部」，无单条彻底删**）。彻底清除是全系统唯一真正删除数据的地方，且删除前留痕。

**Why this priority**: 正交于 Story 1/2，可独立交付。治"垃圾堆成山"，但不在关键路径上（通知闭环不依赖它）。

**Independent Test**: 删一条事项 → 回收站可见 → 复活回到删前状态 / 一键清理后物理删除（原文 raw_inputs 仍在）；被删信息从原视图消失。

**Acceptance Scenarios**:

1. **Given** 一条 todo 事项，**When** 我删除它，**Then** 追加一条 status=trashed 的版本（不是新表、不是旁路删除），它从看板消失、进入回收站；版本链可查"谁在何时把它删了、删前是什么状态"。
2. **Given** 回收站里一条已删事项，**When** 我点「恢复」，**Then** 追加一条版本、status 回到**删前的值**（todo 就回 todo，done 就回 done）。
3. **Given** 一条通知，**When** 我删除它，**Then** 同样进回收站、可复活（通知与事项共用同一删除机制——都靠 itemId 挂在同一条版本链上）。
4. **Given** 回收站里同时有 trashed ≤15d 与 >15d 的信息，**When** 我点「一键清理」按钮（`POST /api/trash/purge` 类端点），**Then** 物理清除所有 >15d 的；**≤15d 的保留**。回收站内**不提供**删除入口与「清空全部」（用户 2026-10-16 定：回收站里只统一清理 >15d）。
5. **Given** 物理清除发生时，**When** 清除执行，**Then** 删 item_versions/evidence/item_views 中挂该 itemId 的行，**raw_inputs/fragments/uncertain_inputs 不动**，删前 stderr 留痕"删了什么、原状态"。
6. **Given** 一条被彻底删掉的信息，**When** 我事后想查，**Then** 看板/回收站都找不到它（这是预期），但其**原文批次仍在原文档案可检索**（raw_inputs 永不删）。

### User Story 4 - 图标与分类表述重整 (Priority: P3)

**看板 / 通知 / 回收站 / 存疑库审核 / 流水 各有清晰的活动栏入口图标**；"消化状态"这类页内状态图标与入口图标语义独立、不互相冒充；分类表述统一为"信息 = 事项 + 通知，回收站另立区域"。

**Why this priority**: 体验收口。依赖 Story 1/2/3 的入口落定，最后做。

**Independent Test**: 活动栏图标各自可辨、语义不混；文档（00 契约/01 规格/CLAUDE.md）术语统一、无新旧并存。

**Acceptance Scenarios**:

1. **Given** 活动栏，**When** 我查看，**Then** 看板 / 通知 / 回收站 / 存疑库审核 / 流水 各有独立且语义清晰的图标（消化"状态"不用事项图标冒充；按含义尽可能选更合适的，语义不混）。
2. **Given** 任一涉及"事项/通知/回收站"的文档或界面文案，**When** 阅读，**Then** 口径统一，旧术语无残留。

### Edge Cases

<!-- 边界形态一次枚举（边界加固三规矩①）——按 null/缺席/脏值/越界/并发/跨用户 分层 -->

- **识别边界（U1 已定：不动机制）**：像通知又像事项的消息——判据归 agent0（提示词尽可能描述"什么信息值得保留"，不新增机械判据机制）；纠偏途径 = 后续信息到来时 `update_item`（含 kind 切换）。
- **通知的 ddl（OQ-2 已定）**：agent0 产出 dueDate 给通知 → **整条拒收**（见 US2-3）。
- **混合批次**：同一条原文可同时产出事项与通知（变更清单里两类并存）；各自证据链独立保留。
- **kind 切换与 ddl（已定）**：task（ddl 有值）→notice 无法满足"通知无 ddl"、元素"只增改不删"（不为转换开删除口子）→ **整条拒收**——"通知必无 ddl"的直接执行，**非额外限制**（用户 2026-10-16 定）；**task（ddl 留空）→notice：允许**（留空 = 无 ddl 值，目标形状满足）；notice→task 不限（事项必须有 ddl、可留空）。
- **删除中事项的复活目标状态**：「删前状态」取值逻辑走版本链（复活回删前值，含 done/todo；archived 已随本批取消，无需再覆盖）。通知同理：删前恒 todo → 复活回 todo。
- **重复删除**：对一条已 trashed 的信息再点删除——幂等，不重复追加无意义版本。
- **彻底删与证据**：彻底删事项时，挂在它下面的 evidence 行级联删除；fragments/raw_inputs 一律保留（证据终端不破）。
- **15 天口径（U13 已定）**：15 天按**进入 trashed 的时刻**算（不是创建时刻）；时区按北京墙钟（D-97）。
- **多用户**：回收站/通知按账户隔离；删他人资源 → 404（同现状构造保证）。
- **存量数据（U11 已定：不迁移）**：存量伪事项保持原样（可由用户删除、或后续信息的 update_item 自然修正）；agent0 不回溯扫描，本特性是"加新类"，不是"重分类旧数据"。
- **存量快照无 `kind` 字段**：一律按 `task` 读取（默认，无需数据迁移）——存量条目全为事项，与本条件一致。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供统一的"信息"载体（Item），事项与通知是它的两种 kind，共用版本链/证据/标签/来源信息机制。
- **FR-002**: 系统 MUST 支持 `kind` 字段区分 `task` / `notice`，与 `status`（演化轴）正交分离。
- **FR-003**: ddl 形状约束（kind 的**唯一**约束）——通知（kind=notice）MUST **无** dueDate：结构上没有被排期的可能；事项（kind=task）MUST **有 ddl**（可留空——留空 = 日期未知）。
- **FR-004**: 系统 MUST 提供独立的「通知」入口——**活动栏主视图入口**（最左侧竖栏；与看板/存疑库/流水同级——不是看板里的一段）；通知不进看板三段；按时间倒序展示，含来源徽标与原文入口。
- **FR-005**: agent0 的判定 MUST 从"非事项 → 丢弃沉底"改为"非事项但有用 → 落为通知"；**判据由 agent0 决定，提示词尽可能描述"什么信息值得保留"，不新增机械判据机制**（用户 2026-10-16 定：U1 不动；与"宁可误录入，不可误丢失"同源）。
- **FR-006**: 系统 MUST 提供删除能力：删除 = 追加 `status=trashed` 版本（走 Replay，不新增删除表、不走旁路）。
- **FR-007**: 系统 MUST 提供回收站独立入口——**活动栏主视图入口**（与看板/通知/存疑库/流水同级）；可复活（status 回到删前值）。
- **FR-008**: 系统 MUST 提供回收站清除：**唯一**批量操作 = 「一键清理」按钮 + 端点（清除所有 trashed > 15d 的信息）；**无「清空全部」、无单条彻底删**。清除由用户显式触发，**不做自动定时清除**（不引 cron）。
- **FR-009**: 彻底删除 MUST 只发生在清除环节，且删除前留痕（stderr 记录"删了什么、原状态"）；`raw_inputs`/`fragments`/`uncertain_inputs` MUST NOT 被物理删除。
- **FR-010**: 通知 MUST 与事项共用回收站（同一 itemId 版本链 → 同一删除/复活/清除机制）。
- **FR-011**: 活动栏图标 MUST 区分 看板/通知/回收站/存疑库/流水 等入口，消化"状态"不得用事项图标冒充。
- **FR-012**: 通知/回收站的徽标与提示 MUST NOT 使用「你还有 N 条没看」式愧疚措辞（01§4.14/§8.2 红线）。
- **FR-013**: 变更 MUST 同步文档（00 契约 / 01 规格 / 02 台账 / CLAUDE.md），不留新旧并存。
- **FR-014**: kind 切换 MUST 复用 `update_item` 承载（不新造动作）；**唯一校验 = ddl 形状**（FR-003）——**不做任何其他限制**（不因状态拒转）；task（ddl 有值）→notice → 整条拒收（"通知无 ddl"的执行）（U3；2026-10-16 修订）。
- **FR-015**: 通知 MUST 支持修改与更替（U4：复用 `update_item`，同一性判定沿用 agent0 现状）；系统 MUST NOT 建立通知↔事项的自动关联机制（U2：不做跨条关联）。
- **FR-016**: 通知 MUST 有「已读」状态（复用 `item_views`，点开即消）；通知行右缘 MUST 提供删除按钮。
- **FR-017**: 删除入口（按钮/对话）在看板行、通知行、对话均可用；展开详情体内不加按钮（D-89 先例）；**回收站内 MUST NOT 提供删除**（回收站内仅：恢复 + 一键清理 >15d）。
- **FR-018**: 系统 MUST 取消「归档」状态、只保留完成（用户 2026-10-16 定：归档与完成体感相近、几乎用不上）。`status` 去掉 `archived`（第一刀后事项枚举 = `todo/done`；第二刀回收站再加 `trashed`——`trashed` 是两 kind 共有的删除态，见 Key Entities）。看板由四段并回三段（日期未知 / 已排期 / 已完成）；归档按钮 / 归档路由 / `archive_item` 动作 / 归档段全部移除。**存量 `archived` 数据 MUST 迁移为 `done`**（schema 迁移，SCHEMA_VERSION +1）——因读路径 `ItemSchema.parse` 对收窄后的枚举零容忍，不迁移则存量归档事项令全站读路径 500；迁移只改 `status` 值，不删版本链、不动其它字段。

### Key Entities *(include if feature involves data)*

- **分类总览**：信息 = 事项（日期未知 → 已排期 → 已完成 三段）＋ **通知**（独立入口）；**回收站 = 独立区域**（跨两类，非类型）。
- **Item（信息）**：统一载体。`elements[]`（通知同样套用，但 dueDate 缺席）+ `tags[]` + `kind`（task|notice，新增）+ `status`（事项：todo/done/trashed；通知恒 todo，删除→trashed、复活→todo）。持久化单位仍是"信息"（追加式版本链）。
- **kind（类型轴）**：新增字段，快照内。取值 `task`（事项）/ `notice`（通知），与 status 正交；可切换（复用 update_item）；**唯一形状约束 = ddl**：`notice` 无 ddl；`task` 必须有 ddl（可留空——留空 = 日期未知）。
- **status（演化轴）**：事项 todo→done→（trashed）；通知恒 todo（"活跃"= 未被删，不造 active 字面量）→ trashed → 复活回 todo；"这是通知、不用完成"由 `kind` 表达，不靠 status。trashed 是删除态、不是类型。
- **回收站（trashed 态）**：不是独立实体，是 status 的一个值；UI 上是活动栏独立入口（存储与视图分离）。删除/复活/清除都是版本链追加与（仅在清理时）物理删除。列表：两类混合、行标 kind、按进入 trashed 的时刻倒序；条目可查看（展开体同款）与恢复。
- **raw_inputs / fragments / uncertain_inputs**：原文档案与存疑库，永不随事项/通知删除。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一条"课改地点"类群消息进站后，分钟级消化内出现在「通知」页，用户无需翻群即可得知。
- **SC-002**: 通知 100% 不进入看板三段（看板装配的过滤可被测试断言）。
- **SC-003**: 删除一条信息后，回收站可见、版本链可查删除留痕、复活后回到删前状态；整个流程无需新增数据库表。
- **SC-004**: 彻底删除后，`raw_inputs` 原文档案仍可检索到该批次（证据终端不破），有测试断言。
- **SC-005**: `npm run check`（tsc+eslint+vitest）与 `npm run check:dead`（knip）全绿；测试在真实入口（HTTP/真实组件）断言用户所见。
- **SC-006**: 通知闭环（Story 1）可独立演示；回收站（Story 3）可独立演示——两者互不阻塞。

## Assumptions

- **命名**：统一载体沿用 `Item`（全量换词延后、不在本批——用户 2026-10-16："算了算了，先不改"）；`kind` 取值 = `task`（事项，"事项"的英语）/ `notice`（通知）。
- **动作词**：沿用 `create_item` / `update_item` + `kind` 字段区分；不新造 `create_notice`（OQ-5 已定）。
- **通知不是知识库**：本特性只做"通知"这一类，**不点亮 00 契约右侧的"知识"节点**、不动 `search_kb` 桩（恒空不变）。知识库仍是独立延后项（L6）。这是用户明确的选择（走"独立入口的通知"，而非"AI 知识库/主题聚合"）。
- **不做自定义分栏/per-partition prompt**：用户已否掉；分类是系统固定的（信息 = 事项 + 通知），用户侧只有筛选/查看，不建容器。
- **第一版不引持久 cron**：15 天清除靠用户显式触发的「一键清理 >15d」按钮；不做自动定时清除。
- **通知的 tag 可缺席**：tag 与事项共用一套词（数据层可同挂），不是通知的必需字段；判不出归类时留空，不编默认；当前 UI 不做跨视图聚合。
- **单用户即多用户形态之一**：隔离按现有构造保证，无新增攻击面。

## 交付拆分（用户 2026-10-16 定：拆）

两个正交子系统，分两刀（先跑通一次完整业务循环再谈下一个——纪律 I）：

1. **第一刀（核心，P1）**：Story 1 + 2 + 4 —— 通知类别（kind + 独立入口 + 判据转向 + tag 共用 + 图标）＋ **FR-018 取消归档**（status 收窄 + 存量迁移 + 看板三段化 + 归档入口/动作移除）。通知落地同时把看板重搓为三段、跑一次 schema 迁移——同一刀里"加通知"与"去归档"都改看板与 status 枚举，合并没有额外 schema 成本。做完"不看群"闭环 + 三段看板，系统可独立验收。
2. **第二刀（正交）**：Story 3 —— 回收站（trashed 态 + 独立入口 + 复活/一键清理/物理清除）。

全量换词（item→…）不在两刀之内（用户：先不改）。

## 开放问题

- **OQ-4**：图标选型——**已定（2026-10-16）：通知 = `Inbox`、回收站 = `Trash2`**（两枚均为活动栏正式一级入口、各自专属图标）。栏内排位：**已定**——`看板 → 通知 → 存疑库 → 流水 → 回收站`（通知紧挨看板、最高频；回收站低频置末）。
- **OQ-8**：删除/清理的确认手势——**已定**：行内删除**一步进回收站**（可复活、不弹确认，与完成同款）；「一键清理」**二次确认**（不可逆；文案说明原文档案不受影响）。对话删除经前台围栏工具（同 `resolve_uncertain` 款式）——**纳入本批**。
- **OQ-9**：检索可见性——**已定**：agent0 检索面**必须**涵盖通知（更新/更替的前提）；前台对话**可查通知（只读）**，@ 提及候选**收录**通知；`trashed` 条目**一律排除**出所有检索面。
- **OQ-10**：活动栏徽标——**已定**：通知入口**有未读则显示数字**（纯计数、非愧疚式）；回收站**不显示**计数。
- **OQ-11**：通知排序与更新提示——**已定**：按「最近更新」倒序（有更新即上浮）；更新后**重新标未读**（内容变了，值得重看一眼）。
- **OQ-12**：对 trashed 条目的写操作——**已定**：围栏**拒收**（trashed 视为不可写，要改先恢复）——防 digest 竞态把已删条目悄悄改活。

> 已定备忘（2026-10-16）：
> OQ-1（像通知又像事项的取向）→ 判据归 AI，提示词尽可能描述，不新增机械机制（U1 不动）。
> OQ-2（通知产出 dueDate）→ **拒整条**。
> OQ-3（启动清扫挂载点）→ 作废：不做启动清扫，改为用户显式触发的「一键清理」按钮。
> OQ-4（图标/排位）→ 通知=`Inbox`、回收站=`Trash2`，均为一级入口；排位 `看板→通知→存疑库→流水→回收站`。
> OQ-5（动作词）→ 沿用 `create_item` + `kind` 字段（取值 task/notice），不新造 `create_notice`。
> OQ-6（15 天口径）→ 固定 15 天，首版不做设置项；按进入 trashed 的时刻算（U13）。
> OQ-8（确认手势）→ 行内删除一步进回收站；一键清理二次确认；对话删除经前台围栏工具（本批）。
> OQ-9（检索可见性）→ agent0 检索面涵盖通知；前台可只读查通知 + @ 收录；trashed 全检索面排除。

> OQ-11（排序）→ 最近更新倒序 + 更新重标未读。
