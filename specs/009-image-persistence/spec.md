# Feature Specification: 图片持久化（前台上传 + 信源图片缓存）

**Feature Branch**: `009-image-persistence`

**Created**: 2026-10-20

**Status**: Draft

**Input**: 用户 2026-10-20 多轮决策：
- 「我想做前台图片上传来着，但是这就涉及到图片持久化了，不过正好也对可以和 qq 那边的图片持久化一起做，不会用户看不到图片了」
- 「都没问题」「给 5mb 吧」→ 后收窄为「压缩策略干脆大于 2mib 就触发吧，压缩到 2m 以下，然后我们重新插值」
- 「我觉得这样设计好冗余，能否只要一个 expiredate 之类的，agent0 工作完成之后自动更新；如果更新不到（被删除了）那就算了不要了」
- 「唯一最麻烦的就是判定 agent0 到底有没有引用到证据，但这刚好是我们约定好的特别的设计」
- 依赖选型：**sharp**（2026-10-20 用户拍板）
- 补充拍板（2026-10-20 复查）：**被证据引用的图延长到 90 天**；**动图超限走压缩**（不是拒收）；**前台 v1 不直接读图**（上传的图交给 agent0 消化）。

## User Scenarios & Testing

### User Story 1 - 前台上传图片 (Priority: P1)

用户在对话里直接贴一张图（截图/海报/照片），图片随消息进入管线；agent0 能读到图里的信息并据此建事项/通知；之后在事项详情与证据引文里能直接看到这张图，而不是一串链接。

**Why this priority**：前台是用户最常用的入口；没有它，图片只能从 QQ 群来。

**Independent Test**：在对话里粘贴一张带日期的截图 → 发出 → 事项出现且带「多模态/图片」标签 → 详情里能看到图。

**Acceptance Scenarios**：

1. **Given** 对话输入框，**When** 用户粘贴/选择一张 ≤2 MiB 的 JPEG，**Then** 输入框旁出现缩略图（**此时尚未上传**，只是本地预览），可移除。
2. **Given** 输入框已有预览图，**When** 点发送，**Then** 图片先上传、成功后消息发出；落档正文 = 用户文字（若有）+ 空行 + 单独一行 `[图片](/api/media/<id>)`。
3. **Given** 上传的图片 >500 KiB 且 ≤20 MiB，**When** 发送，**Then** 服务端压缩到 500 KiB 以内后存储，用户与 agent0 都能看到压缩后的图。
4. **Given** 上传失败（超限/不是图片/网络），**When** 发送，**Then** 消息不发出、错误可见，预览图保留可重试。
5. **Given** 未登录或属于其他账户，**When** 请求 `/api/media/<id>`，**Then** 401/404，不泄露图片。

---

### User Story 2 - 信源图片进站即缓存 (Priority: P1)

QQ 群消息里的图片（原文占位 `[图片](url)`）在进站时由服务端后台抓取并缓存；即使原链接过期，用户在原文/证据里仍能看到图。

**Why this priority**：QQ 图片链接约小时级过期，不缓存等于永久丢失。

**Independent Test**：模拟一条带图片 URL 的进站批次 → 缓存文件与 media 行出现 → 断开原 URL（或等到过期）后，详情仍能显示图片。

**Acceptance Scenarios**：

1. **Given** 一条含 `[图片](http…)` 的 nc 消息进站，**When** 落档完成，**Then** 后台下载并缓存；原文**逐字不变**。
2. **Given** 下载失败（超时/非图片/超限），**When** 进站完成，**Then** 不缓存该图，stderr 留痕；原文占位保留，界面回退原链接。
3. **Given** 同一图片 URL 已在缓存中，**When** 再次进站，**Then** 不重复下载。

---

### User Story 3 - 大图自动压缩 (Priority: P2)

超过 500 KiB 的图片在存储前由服务端压缩（质量阶梯 + 降采样重插值），目标 500 KiB 以内（用户 2026-10-21 定）；完成后 agent0 仍可读取（**agent0 的单图读取上限仍是 2 MiB**）。

**动图（GIF / 多帧 WebP）同样走压缩**（用户 2026-10-20 定）：先降帧率/丢帧，仍超则按静图档继续压。代价是动画可能变短或变成单帧——**压缩器必须在界面与日志里说明这一点**，不静默。

**Acceptance Scenarios**：

1. **Given** 一张 8 MiB JPEG，**When** 上传/进站，**Then** 存储大小 <2 MiB，图片可正常查看。
2. **Given** 一张压缩到最低档仍 >500 KiB 的静图（如高噪点照片），**When** 上传/进站，**Then** 拒收并给出可见理由（不存一张超限的图）。
3. **Given** 一张 >500 KiB 的动图，**When** 上传/进站，**Then** 压缩（必要时降帧/转单帧）到 500 KiB 以内后存储，并提示「动画已压缩」。
4. **Given** HEIC，**When** 上传，**Then** 拒收并提示转 JPEG（预编译 sharp 不含 HEVC 解码）。

---

### User Story 4 - 缓存留存与清理 (Priority: P2)

留存分三档（用户 2026-10-20 定）：

| 图片状态 | 到期时刻 |
|---|---|
| **入库时**（此后未触发下面两条） | 基础留存：按大小反向 7–14 天 |
| agent0 读过、证据**未引用** | `min(原值, 读取时刻 + 3 天)`——只提前、不延后 |
| 证据**引用了**（引文含该图占位） | `max(当前, 引用时刻 + 90 天)`——长期保留，证据链不断 |

到期自动清理，删除可见留痕。

**Acceptance Scenarios**：

1. **Given** 一张 100 KiB 图片，**When** 入库，**Then** 基础留存约 13.7 天；一张 2 MiB 图片约 7 天。
2. **Given** agent0 读取但未在证据中引用，**When** digest 完成，**Then** 该图 `expiresAt` 改为 `min(原值, 读取时刻 + 3 天)`——本来就少于 3 天的**不会被延长**。
3. **Given** agent0 读取且证据引用了该图，**When** digest 完成，**Then** 该图 `expiresAt` = `max(当前, 引用时刻 + 90 天)`——即使已被缩到 3 天也能救回。
4. **Given** 同一张图被多次引用，**When** 每次都写入证据，**Then** `expiresAt` 以最后一次引用时刻 + 90 天为准（日期永不回退）。
5. **Given** 已过期图片，**When** 清理器运行，**Then** 文件与行被删除，stderr 记录张数与字节数。

---

### User Story 5 - 过期可见性 (Priority: P3)

缓存过期后界面不静默。判据按占位来源分两种：

- 占位是**本地媒体**（`/api/media/<id>`，即上传图）→ 显示「图片已过期」
- 占位是**外部链接**（QQ 图等）→ 回退为原链接（可点，但对方多半也已失效）

---

### Edge Cases

- **上传时机**：选择/粘贴只做本地预览，**点发送才上传**——不会因"选了又没发"留下孤儿文件。
- 一条消息最多 **1 张**图（v1）；已有预览时再粘贴/选择 → 替换，不累加。
- 上传成功但消息发送失败：该图按基础留存自然过期（无孤儿清理逻辑）。
- 同一内容多次上传：按 sha256 去重，只存一份（行复用，`expiresAt` 取较晚者）。
- 同一图片两个不同 URL（nc）：只保留首个 originUrl，第二处回退原链接（不为此加映射表）。
- 图片解码炸弹：像素上限 25MP、输入上限 20 MiB。
- 代理/反代对静态图片的缓存：响应必须 `Cache-Control: private`。
- 回收站清理不删 media（与「原文永不删」同口径）；media 只按 TTL 清理。
- 服务重启：未完成的后台缓存下载丢失——**该批次不会再进站一次**，这张图就是没缓存上；原文占位保留，界面回退原链接。清理器重启后照常运行。
- 文件缺失但行还在（手工删了文件）：`GET` 返回 404；清理器只删行并留痕。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 提供 `POST /api/media`（认证；鉴权先于解析 body），接收原始图片字节，返回 `{ id, url, mime, sizeBytes, animationCompressed }`。
- **FR-002**: 系统 MUST 校验 MIME + 魔数；只收 JPEG/PNG/WebP/GIF/BMP/TIFF；拒收 SVG。
- **FR-003**: 单图输入上限 20 MiB；像素上限 25MP；超限拒收并可见报错。
- **FR-004**: 存储前 >500 KiB 的图 MUST 被压缩到 500 KiB 以内（质量阶梯 → 降采样；动图先降帧/丢帧再按静图压缩）；压到最低档仍 >500 KiB 拒收。**降级必须回报**：动图变短/变单帧 → `animationCompressed`（透明背景填白是存储侧固定行为，不回报——2026-10-21 用户定）。
- **FR-005**: 文件 MUST 存于 `data/media/<uid>/<sha256>.<ext>`；用户库新增 `media` 表（id/mime/sizeBytes/createdAt/expiresAt/originUrl）。
- **FR-006**: `GET /api/media/:id` MUST 要求登录并按账户库校验归属；响应 `Cache-Control: private`、`nosniff`；文件缺失 404。
- **FR-007**: 进站（`ingestBatch`）后 MUST 扫描 `[图片](http…)` 并后台缓存（并发上限 2）；失败 stderr 留痕；原文字节不变。
- **FR-008**: agent0 `fetch_image` MUST 优先解析本地媒体（零网络）；未命中走原下载，成功后持久化。**agent0 单图读取上限保持 2 MiB**。
- **FR-009**: 基础留存 MUST 为 `clamp(14d − size/2MiB × 7d, 7d, 14d)`，按**最终存储大小**计算。
- **FR-010**: digest 结束后，本批 agent0 读过且**未被任何批次的证据引用**的媒体 MUST 将 `expiresAt` 改为 `min(原值, 读取时刻 + 3 天)`（跨批否决：A 批引用过、B 批只读过 → 不缩）；更新 0 行则忽略。
- **FR-011**: 证据引用（引文含该图占位）MUST 把 `expiresAt` 抬到 `max(当前, 引用时刻 + 90 天)`——晚到的引用能把被缩短过的图救回来；多次引用以最后一次为准（日期只增不减）。
- **FR-012**: 清理器 MUST 在启动时与每小时运行一次，删除 `expiresAt <= now` 的文件与行，stderr 留痕。
- **FR-013**: `GetItemResult` MUST 附带 `media` 映射：key = **原文里的占位 URL**（上传图是 `/api/media/<id>`，信源图是原始链接），value = `MediaRef`。前端一次拿全，不做 N+1。
- **FR-014**: 前端 MUST 在事项详情/证据引文/原文弹层中把可解析的 `[图片](url)` 渲染为图片；未命中时按占位来源回退（本地 → 「图片已过期」；外部 → 原链接）。
- **FR-015**: ChatPanel MUST 支持选择与粘贴图片（**每条消息最多 1 张**），选后本地预览、可移除，**点发送才上传**。**前台 v1 不直接读图**——上传的图交给 agent0 消化（用户想看图里的内容时，由 agent0 建出事项/通知来体现）。

### Key Entities

- **Media**：一张缓存的图片；sha256 主键、mime、最终字节数、创建/过期时刻、可选原始 URL。
- **Item/Evidence**：不变；占位文本 `[图片](url)` 仍在原文与引文中逐字保留。

## Success Criteria

- **SC-001**: 前台粘贴图片 → 事项详情可见图片，全链路无手工步骤。
- **SC-002**: 缓存后的 nc 图片在原 URL 失效后仍可显示。
- **SC-003**: 任何存储的图片 ≤500 KiB 且 agent0 可读取。
- **SC-004**: 留存规则在测试中可精确断言（给定 size/读/引用 → 期望 expiresAt；三档边界全覆盖）。
- **SC-005**: `npm run check` 全绿；真实入口断言用户所见。

## Assumptions

- 部署盘为本机 `data/`（bind mount），备份口径 = 整个 `data/`。
- 服务商/浏览器支持标准图片格式；HEIC 不在支持范围。
- 单账户并发上传量小（个人中枢），不需要队列。
- **迁移版本号**：010 先落地，占 `SCHEMA_VERSION` 2→3；009 落地时 **3→4**（两者不自作主张合并）。
